# 学习文档评审指南

本指南用于评审 Tiny Robot 的学习文档是否真正帮助读者完成预期学习任务。它是可重复执行的评审流程；页面类型、结构约束和 Demo 规则以[下一代文档完整性规范](./documentation-standard.md)为准。

评审的目标不是把近期讨论逐条补进正文，而是判断页面在整个学习路径中承担什么职责，以及目标读者能否沿着连续主线获得正确理解。

## 评审先确定页面职责

评审正文之前，先记录以下信息：

- **目标读者**：读者已经知道什么，还不知道什么；
- **唯一主要目标**：读完后，读者应能完成什么或解释什么；
- **主要类型**：学习教程、操作指南、原理说明或参考资料；
- **前置知识**：哪些概念必须由上游页面提供；
- **可观察结果或可查询事实**：页面最终交付的是运行结果、操作结果、机制理解还是精确信息；
- **相邻页面**：前一页提供什么，下一页继续什么。

一页可以包含其他类型的局部内容，但只能有一种主要类型。若无法写出唯一主要目标，或必须依靠两个互不依赖的学习目标解释页面存在的理由，应优先拆页，而不是继续增加章节。

## 三层评审

### 第一层：结构与学习质量

从目标读者视角检查页面是否遵循所属类型的认知顺序，正文在不运行 Demo 时是否仍能建立完整理解，以及概念、场景、边界和下一步是否形成连续主线。

先把页面标题和各级章节标题单独列成提纲：标题应直接表达页面目的、读者动作或稳定主题。若提纲主要由“先看……”“这个示例……”“接下来……”等作者叙事组成，或入口标题要求新读者理解尚未定义的内部术语，应先重构标题和开场，再评审段落细节。

这一层不要求所有页面都回答同一组问题。教程重在学习跃迁，操作指南重在任务完成，原理说明重在因果与边界，参考资料重在准确查询。

### 第二层：事实一致性

学习质量不能替代事实验证。评审同时需要检查：

- 示例字段与当前公共类型一致；
- 可执行示例有类型检查或稳定回归测试保护；
- 图中的关系与类型、契约和永久测试一致；
- 当前能力、后续能力和临时实施材料没有混写；
- VitePress 构建、内部链接和适用的 TypeDoc 检查通过。

### 第三层：陌生读者验证

在第一个端到端 Run、工具流程、Provider 接入和发布等重要里程碑，邀请未参与当前设计讨论的开发者冷启动阅读。让对方完成一个小任务或复述完整链路，记录实际卡点，不预先解释正确答案。

日常 Task 评审完成前两层即可；重要里程碑再增加第三层。

## 按内容类型评审

### 学习教程

学习教程应帮助读者从业务问题出发获得一项新的完整能力。评审时检查：

1. 页面标题是否使用新读者能够理解的动作或结果，并在首段定义后续必需的核心对象；
2. 是否先说明业务问题、目标结果和必要前置知识；
3. 是否在抽象解释前提供最小场景或结果预览；
4. 是否沿主链路逐步引入概念，而不是按源码目录或实现顺序堆叠；
5. 正常流程是否完整走通，再解释关键状态、边界和扩展点；
6. 章节标题是否形成动作与结果清楚、同层级句式平行的提纲；
7. 结尾是否收束本页能力并给出自然的下一步。

教程可以有小结或练习，但不得把固定的“检查你的理解”问答当作必备章节。是否需要练习，应由学习目标决定。

### 操作指南

操作指南应帮助已有必要背景的读者完成一个明确任务。评审时检查：

1. 目标、适用条件和完成标准是否清楚；
2. 前置配置和输入是否可以直接确认；
3. 步骤是否按执行顺序组织，并在关键处提供验证信号；
4. 常见失败是否放在对应步骤附近，恢复方式是否可执行；
5. 是否避免插入会中断任务的长篇原理说明，并通过链接提供深入阅读。

### 原理说明

原理说明应回答系统为什么这样工作以及边界在哪里。评审时检查：

1. 核心问题、适用范围和已有前置概念是否明确；
2. 术语、参与者和责任边界是否先建立；
3. 因果链、状态变化或数据流是否连贯；
4. 关键取舍、不变量、失败语义和扩展边界是否可解释；
5. 示例是否用于验证机制，而不是把页面变成操作步骤集合。

### 参考资料

参考资料应让读者快速、准确地查询事实。评审时检查：

1. 范围、版本和稳定性是否明确；
2. 条目结构是否一致，命名是否可搜索；
3. 类型、默认值、约束、返回值和错误语义是否准确；
4. 示例是否短小并直接说明条目用法；
5. 是否避免承担渐进教学主线，并链接到需要上下文的教程或原理页面。

上述顺序是逻辑约束，不要求页面使用这些文字作为固定标题。

## Demo 审查

Demo 是辅助理解的可观察证据，不是正文成立的前提。读者跳过全部 Demo 后，仍应能理解页面承诺的主线。

一页可以包含多个 Demo。评审每个 Demo 时记录：

- **角色**：快速演示、能力演示、边界演示或扩展演示；
- **局部观察目标**：读者运行后只需观察哪一件事；
- **默认输入与预期结果**：无需猜测如何触发和判断；
- **前置依赖**：是否只依赖正文已经建立的概念；
- **独立性**：不运行其他 Demo 是否仍能理解它；
- **主线关系**：它如何支持当前页面的唯一主要目标。

快速演示通常靠前，用于让读者先看到结果；能力、边界和扩展演示放在相关概念已经建立的位置。不要为了形式完整强行凑齐四种 Demo。

出现以下任一情况时，应优先拆成新页面，而不是继续扩充当前 Demo：

- 引入新的主要业务目标；
- 跨入新的架构层或责任边界；
- 依赖尚未讲解的独立模块或新前置知识；
- 需要先教授一套独立机制，读者才能理解演示；
- 页面为了容纳演示而让正文主线或 Playground 明显过载。

## 跨页面模块审查

单页通过不代表学习路径通过。对一个主题模块还要检查：

- 页面顺序是否由认知前置关系决定，而不是由 Task 编号、目录或开发顺序决定；
- 上游页面承诺的概念是否足以支撑下游页面；
- 正常场景、关键边界和扩展能力是否由最合适的页面承担；
- 同一概念是否只有一个权威定义，其他页面只保留必要摘要和链接；
- 页面之间是否存在重复开场、隐含跳读或相互循环依赖；
- Demo 是否分布合理，而不是集中到一个不断膨胀的综合页面。

“正常场景先走通，再进入边界与扩展”是模块级学习顺序，不要求每一页都同时包含正常、边界和扩展内容。

### 学习依赖审查

评审不能只搜索术语定义。先按[学习依赖闭包](./documentation-standard.md#学习依赖闭包)清点页面中的概念、公共 API、状态、关系、架构角色、模型能力，以及代码、图表、表格和 Demo 标签，再记录它们的首次语义使用位置。

每项依赖只能标记为以下一种已解决方式：

- 属于页面明确声明的目标读者基础；
- 在首次使用前给出最小定义；
- 由主学习路径的前置页面提供，并在当前使用前声明和链接；
- 非线性参考页面在使用前链接权威定义。

解释位于首次使用之后、只在 Demo 内可观察、依赖英文名词互相说明，或者仅以“开发者通常知道”为理由时，都应标记为未解决。包含多个项目概念的复合表达必须拆成多行审查。

完成单页清单后，再把页面之间的“依赖于”关系画成简单有向图或列表。若 A 页面依赖 B、B 页面又直接或间接依赖 A，必须前移共同的最小定义、调整页面顺序或拆分职责，不能用相互链接掩盖环路。

## 建议评审流程

1. 记录目标读者、唯一主要目标、页面类型、读者基础、前置页面和相邻页面。
2. 清点学习依赖，记录每项依赖的首次语义使用位置与满足方式；先确认未解决项，再决定改法。
3. 不运行 Demo，从页面开头读到结尾，确认正文自身能够完成承诺。
4. 按页面类型检查认知顺序，记录第一次失去理解的位置。
5. 清点全部 Demo，标注角色、局部目标、依赖和预期结果。
6. 判断每个 Demo 应保留、移动、合并、删除，还是连同新目标拆到另一页。
7. 沿前后页面继续阅读，检查模块级正常流程、边界和扩展是否连贯，并检查跨页面依赖环。
8. 把问题归类后，先选择重写、合并、移动、拆分、删除或链接，再决定是否增加内容。
9. 核对 API、ADR、契约、实现和验证证据，区分教学问题与事实错误。
10. 修改后重新生成首次使用清单，从目标页面开头读到受影响的下一页，确认未解决依赖为零且没有问答接缝。
11. 运行自动验证并记录仍未覆盖的风险。

全面扫描文档时，应先完成页面类型、主要目标、Demo 和相邻关系的清单，再集中制定整改顺序。不要边发现边追加段落，否则容易把局部反馈再次变成补丁式正文。

## 问题分类

| 分类      | 判断方式                                         | 常见修正                         |
| --------- | ------------------------------------------------ | -------------------------------- |
| 类型错配  | 页面结构与其主要任务不一致                       | 重新定型，重排结构或拆页         |
| 目标缺失  | 不知道为什么读或读完能做什么                     | 明确唯一主要目标和可观察结果     |
| 顺序跳跃  | 当前内容依赖后文才解释的概念                     | 前移最小定义或调整页面、模块顺序 |
| 依赖缺口  | API、状态、关系或能力在首次语义使用前没有解决    | 补最小定义、前置声明或权威链接   |
| 依赖环路  | 页面直接或间接互相要求作为前置                   | 前移共同定义、重排顺序或拆分职责 |
| 场景断裂  | 概念正确但无法放回完整业务流程                   | 补就地示例或重建场景主线         |
| 抽象过早  | 尚未看到问题或行为就先解释大量结构               | 先展示问题、结果或最小主链路     |
| 边界模糊  | 无法预测失败、安全或生命周期结果                 | 补关键边界与稳定结果             |
| 扩展混乱  | 把未来字段或开发记录当成扩展性                   | 改为稳定扩展点、责任层和不变量   |
| Demo 依赖 | 跳过 Demo 后正文不成立，或 Demo 彼此依赖才能理解 | 补正文说明，降低依赖或拆分演示   |
| Demo 过载 | 一个 Demo 同时教授多个新概念或承担多个目标       | 缩小观察目标、拆 Demo 或拆页     |
| 拆页遗漏  | 新目标、新层或新前置知识被塞进原页               | 建立新页面并补足上下游链接       |
| 事实漂移  | 示例、图或文字与公共类型不一致                   | 修正文档并补必要的自动保护       |
| 入口错误  | 页面按 Task、目录或内部术语组织                  | 改为读者目标和认知前置关系       |
| 补丁累积  | 新段落各自正确但整页像连续问答                   | 回到提纲，重写、合并、移动或拆分 |
| 职责混杂  | 一页同时承担多个互不从属的主线                   | 保留唯一主要职责，其余移出并链接 |

评审反馈应描述读者在哪里失去理解以及缺少什么信息，避免只写“这里不清楚”。用户的问题和异议是定位缺陷的证据，不是可直接复制到正式文档的标题或正文。

## 补丁累积审查

根据会话反馈修改过的页面，需要额外完成一次整页审查：

- 如果不知道最近的讨论，读者能否理解各章节为何存在、为何出现在这里？
- 页面类型、唯一主要目标和实际结构是否仍然一致？
- 标题是否像在直接回答某次追问；如果会，它是否本来就属于 FAQ 或故障排查？
- 新内容是否重复前文定义，或把后续原理和参考细节提前塞进教程？
- 跳过所有 Demo 后，正文是否仍能完成页面承诺？
- 多个 Demo 是否各有局部观察目标，是否有应当拆页的新目标或新前置知识？
- 删除新增标题后，正文是否更适合并入已有章节？
- 新概念若需要独立复用，是否应移到原理说明或参考资料，只在当前页保留最小解释和链接？
- 本次修改是否需要同步调整前置页、下一步链接、导航名称或示例顺序？

通过标准不是“每个新增段落都正确”，而是整页看不出修改轮次，读者能沿一条连续主线完成预期学习跃迁或查询任务。

## 通过条件

一次学习文档评审只有同时满足以下条件才通过：

- 页面类型明确，唯一主要目标与结构一致；
- 教程、操作指南、原理说明或参考资料满足各自的核心约束；
- 主路径中没有必须跳到后文才能理解的未定义概念；
- 首次使用清单覆盖标题、正文、代码、图表、表格和 Demo，未解决依赖为零；
- 跨页面依赖不存在环路，前置链接都位于首次语义使用之前；
- 跳过 Demo 后正文仍然成立，每个保留的 Demo 都有清楚的角色和局部观察目标；
- 新业务目标、新架构层或新前置模块没有被错误塞进当前页面；
- 模块级正常场景、关键边界和扩展能力的学习顺序连贯；
- 页面结构不依赖近期会话，没有逐轮追加形成的问答接缝或重复概念；
- 示例、图、API、ADR、契约、实现和测试没有相互矛盾；
- 适用的自动文档检查与站点构建通过；
- 剩余未覆盖能力被描述为清晰的当前边界，而不是含混承诺。

评审者是学习质量的核心验收者，但“我理解了”不能替代事实一致性验证。反过来，构建和类型检查通过也不能证明文档具有可学习性。
