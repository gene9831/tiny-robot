# 下一代文档完整性规范

本文是 AI 和维护者检查下一代架构文档是否足够可理解的统一门禁。它不要求每次改动都增加大量文字，而是要求重要概念不能只存在于类型名、英文注释或实现代码中。

## 文档目标与读者

这套文档既服务参与设计和评审的维护者，也服务第一次接触 Tiny Robot Runtime 的开发者。它必须同时支持两种使用方式：

- **连续学习**：读者沿着一条明确路径，从完成最小场景开始，逐步理解公共边界、领域状态、执行流程和扩展方式；
- **按需查询**：已经具备背景知识的读者可以直接解决一个问题、查找一个公共符号或核对一项设计依据。

连续学习是新读者的主入口。评审记录、实施任务编号和临时计划不能成为理解产品能力的前置条件。按需查询页面可以脱离主路径使用，应清楚说明适用范围，并在必要时就地定义概念或链接稳定的权威来源；它们不必加入教程顺序，也不能要求读者先完成整条学习路径。

文档的成功标准不是“覆盖了所有类型”，而是读者能够逐层回答：

1. 这个框架解决什么问题；
2. 在一个具体场景中，输入、边界、状态和结果怎样关联；
3. 为什么职责和数据采用当前分工；
4. 失败或越界时会发生什么；
5. 需要增加能力时，应该扩展哪一层并保持哪些不变量。

## 文档分工

| 载体                 | 唯一职责                                       | 不应该承载                   |
| -------------------- | ---------------------------------------------- | ---------------------------- |
| `CONTEXT.md`         | 一句话定义领域术语，保持统一语言               | 实现步骤、状态机细节、教程   |
| `docs/adr/`          | 记录长期决策的背景、选择、理由和后果           | 教程前置要求、学习路径导航   |
| `docs/contracts/`    | 使用 MUST/SHOULD/MAY 记录已批准的规范性约束    | 未批准设计、入门解释         |
| `docs/architecture/` | 集中记录稳定分层、职责和依赖关系               | 从零教学、教程完成顺序       |
| `docs-next/`         | 中文概念说明、局部图例、场景、设计说明         | 重复维护完整 TypeScript 签名 |
| Runtime TSDoc        | 英文符号级语义、参数、返回值、不变量和安全限制 | 长篇教程、跨模块总览         |
| 永久测试             | 证明公共示例和关键不变量真实可执行             | 仅用于实现过程的临时检查     |

发生冲突时，已批准的契约高于解释文档；解释文档必须指出差异，不能悄悄改写契约。

## 内容类型与学习路径

文档采用四种内容职责，但不要求顶栏、侧栏或目录机械地按四类分组：

| 内容类型 | 回答的问题                               | 主要写法                           | 不应混入                        |
| -------- | ---------------------------------------- | ---------------------------------- | ------------------------------- |
| 学习教程 | “怎样建立使用和理解这套框架的能力？”     | 受控场景、渐进主线、连续可观察结果 | 大量选项、完整 API 清单、设计史 |
| 操作指南 | “面对一个明确问题，怎样正确完成目标？”   | 以实际目标组织步骤和判断分支       | 从零教学、无关原理展开          |
| 原理说明 | “为什么这样设计，它与其他部分怎样关联？” | 职责、机制、权衡、不变量和边界     | 冒充可执行步骤、重复完整签名    |
| 参考资料 | “精确名称、签名、取值和约束是什么？”     | 完整、稳定、可检索的结构化事实     | 教学叙事、隐含操作顺序          |

目录位置不能代替内容分类。`examples/` 中的页面可能是教程、操作指南、原理验证或可运行参考，必须根据读者目标确定主要类型；不得新增一个职责含混的“示例文档”类型。ADR 和契约是设计证据与规范载体，不为套入四类学习页面而改写自身结构；文档站可以把它们作为按需查询入口展示。

主学习路径可以依次连接不同类型的页面，但每个页面只有一个主要职责。例如，一个学习模块可以先用教程建立经验，再链接原理说明解释设计理由，由操作指南帮助迁移到真实业务，并把精确签名交给 API 参考；不能把四种职责平均混进同一篇长文。

导航同时维护两种结构：

- **学习顺序**按读者的前置知识排列，作为首页、侧栏和教程页末的主线；
- **查询入口**按读者目标进入操作指南、API、术语来源、ADR 和契约，不改变主线顺序。

实现依赖图不等于学习路径。一个实现 Task 可以同时交付多个需要分开讲授的概念；多个实现 Task 也可以共同完成一个端到端学习场景。文档应按认知前置关系组织，不能仅按代码提交顺序、Task 编号、目录结构或 Demo 组件排列。

## 正文共同底线

写作前必须确定目标读者、唯一主要目标和载体职责，但这些是编辑判断，不要求机械写成“目标读者”“前置知识”章节。正文共同遵守：

- 教程、操作指南和承担渐进解释的页面在需要时说明适用范围与前置知识；教程与操作指南还要说明读者将获得的结果。
- ADR 应能从决策背景直接进入选择、理由与后果；契约和 API 参考应能直接进入适用范围与精确信息。它们不得要求读者先完成教程，也不必伪造学习顺序。
- 正文使用当前有效设计语言，不依赖会话记录、实施计划、评审过程或作者当时的推理顺序。
- 新的学习依赖在读者实际需要的位置渐进出现，并在首次语义使用前解决；不集中预加载完整架构，也不先使用、后补解释。
- 当前能力、稳定边界和后续能力明确分开；尚未实现的未来能力不能充当现行扩展点。
- 正文独立说明与页面目标相关的输入、结果或精确信息；读者跳过任意或全部 Demo、图例和交互后仍能理解结论。
- 页面按自身职责自然收束，不统一设置“检查你的理解”、课后练习、固定总结或扩展章节。
- 只有存在明确认知关系时才提供主线下一步或按需链接；参考资料不必伪造学习顺序。

这些约束是写作底线，不是固定标题模板。标题必须描述当前主题和读者目标，不能把本节列出的概念名称机械复制成页面提纲。

## 标题与提纲规则

标题是页面的信息架构，不是作者讲述过程的旁白。只阅读页面标题和各级章节标题时，读者也应该能判断页面目标、内容范围和推进顺序。

- 页面标题必须反映页面的主要目的。教程和操作指南优先使用读者要完成的动作或得到的结果；原理说明和参考资料使用明确的主题、关系或机制。
- 面向新读者的入口标题不得依赖尚未解释的项目内部术语。必须使用内部术语时，先在页面开头用日常语言定义其职责，再在后续标题、代码和图中使用。
- 任务型章节使用具体动作或结果，例如“提交一个问题”“从 Snapshot 读取回答”；概念型章节使用明确的名词短语，例如“模型接入信息的边界”。同一层级应保持平行的句式和抽象层次。
- 每个章节标题必须能脱离上下文表达稳定主题。不得用“先看最终结果”“一次提问经过什么”“这个示例验证什么”“当前这条路径能做到什么”等作者叙事、指代语或会话式问句代替实际主题。
- 把标题单独组成目录进行检查：目录应像一份简明提纲，而不是阅读指令、写作过程或问题清单。重要关键词和读者目标应尽量出现在标题前部。
- 只有正文出现了新的、可独立扫描的主题时才增加标题。不能为了缩短段落制造空泛的“背景”“概述”“说明”“小结”，也不能用连续标题代替必要的过渡正文。

这些规则借鉴英文技术写作中“任务型标题使用动作短语、概念型标题使用名词短语”的原则。中文不机械翻译英文语法，但必须保持相同的信息功能：任务标题指出要做什么，概念标题指出要理解什么。

## 四类页面的结构约束

下面的顺序描述信息如何展开，不要求使用同名标题，也不要求每个可选环节都出现。

### 学习教程

教程让第一次接触该能力的读者通过受控业务场景建立经验和理解。推荐顺序是：业务场景 → 目标与前置知识 → 结果预览或快速 Demo → 最小主路径 → 正文说明可观察结果 → 关键机制 → 按需穿插能力、边界或扩展 Demo → 能力收束 → 主线下一步。

教程必须先走通最小但完整的正常路径，每次只增加一个主要认知负担。失败、变体和扩展只在正常结果已经成立后出现。学习结果通过正文描述的可观察结果和读者已经完成的主路径收束，不要求附加问答式测验。

### 操作指南

操作指南服务已经知道目标的读者。推荐顺序是：适用场景 → 前置条件 → 推荐方案 → 操作步骤或判断分支 → 完成条件 → 常见失败与恢复 → 相关原理和参考。

操作指南围绕真实任务组织，可以有多个入口、出口和判断分支；只保留完成任务需要的解释，不从零教授领域模型，也不为了完整性复制 API 参考。

### 原理说明

原理说明帮助读者理解系统为什么这样工作以及各部分怎样关联。推荐顺序是：具体现象或已知场景 → 核心模型 → 职责与关系 → 设计理由 → 不变量和边界 → 对使用或扩展的影响 → 相关教程、契约或参考。

场景用于建立上下文，不要求读者执行步骤。原理说明可以讨论取舍和备选视角，但只保留具有长期意义的理由；扩展性只说明当前稳定扩展点、负责层和必须保持的不变量。

### 参考资料

参考资料用于准确、快速地查询事实。推荐顺序是：适用范围与版本 → 精确名称或签名 → 字段、取值和默认值 → 约束与错误 → 最小示例 → 权威来源。

参考资料不要求业务场景、教学叙事、学习总结、主线下一步或 Demo。示例只帮助解释精确用法，不能暗示未声明的操作顺序。

## 跨页面学习模块

一个完整能力可以由多篇页面共同建立：教程提供场景、主路径和可观察结果；原理说明解释职责、机制、边界和不变量；操作指南帮助迁移到真实业务；参考资料提供精确 API 和约束。

不是每项能力都必须同时拥有四类页面。只有存在真实读者需求时才新增页面，并通过主学习路径和按需查询入口连接。模块应覆盖业务动机、最小正常结果、必要机制和一个能纠正核心误解的真实边界，但这些内容可以分布在不同页面中。

同一连续场景可以跨模块演进，但每次只增加一个主要认知负担。例如先完成单轮文本回答，再增加多个 Conversation，再解释模型调用投影，最后才进入多 Step 工具流程。不得为了展示系统全貌，在入门页面一次引入全部最终组件。

## Demo 规则

Demo 是辅助观察材料，不是独立内容类型，也不承担正文唯一证据。同一页面可以包含多个 Demo，但页面仍只有一个主要读者目标，每个 Demo 只能承担一个局部观察目标。

- Demo 前说明它帮助观察什么、默认输入是什么、预期结果是什么；Demo 后只补充它揭示的关系或差异。
- 正文不能以“如你刚才所见”为成立前提；读者跳过一个或全部 Demo 后仍能获得完整结论。
- **快速 Demo** 在读者具备最小前置知识后的最早自然位置出现，用最少控件预览核心结果，不承担完整讲解。
- **能力 Demo** 紧邻对应能力的正文说明，帮助观察新的输入、状态或结果；它不能依赖读者记住未说明的前一个 Demo 内部状态。
- **边界 Demo** 在正常能力已经成立后出现，只选择最能纠正常见误解的失败、安全或生命周期边界。
- **扩展 Demo** 在核心能力和稳定扩展点已经解释后出现，展示同一能力怎样适配新场景。如果它引入新的主要业务目标、架构层或前置模块，必须拆成后续页面。
- 多个 Demo 应小而聚焦，可以复用底层组件或场景数据，但不能为了减少文件数量合并成控制项过多的综合 Demo。
- 原理说明中的 Demo 紧邻它所验证的概念；综合 Playground 独立成页，并明确主要内容类型、适用范围和前置知识。

## 从会话反馈到正式文档

会话中的问题、异议和追问用于发现读者在哪里失去理解，不直接决定正式文档的标题、段落和出现顺序。即使用户已经授权修改文档，AI 和维护者也必须先把反馈转换成文档问题，再选择结构操作。正式正文应当脱离原会话独立成立，不能要求读者知道“之前问过什么”。

每次根据会话反馈修改学习文档时，按以下顺序处理：

1. **提炼阅读障碍**：记录读者在哪个位置无法继续，以及缺少哪类信息，不复制问句充当需求标题。
2. **判断根因**：区分概念缺失、学习顺序错误、场景或证据不足、边界不清、事实错误与页面职责混杂。
3. **确认页面职责**：重新确认目标页面属于学习教程、操作指南、原理说明还是参考资料，并写出它唯一的主要学习目标。
4. **复核提纲和上下游**：检查问题应该在本页解决、在前置页提前铺垫，还是在后续原理或参考页展开。
5. **选择结构操作**：优先使用重写、合并、移动、拆分、删除重复内容或增加链接；只有现有提纲确实缺少一个必要槽位时才追加章节。
6. **改写为稳定叙事**：使用当前有效的领域语言，把结论放在读者实际需要它的位置，不按会话发生顺序排列。
7. **整页重新验收**：从页面开头重新阅读，并继续读到受影响的下一模块，确认没有新增前置知识、重复解释、问答接缝或主线中断。

除非目标页面明确是 FAQ、故障排查或访谈记录，否则不得使用“为什么……”“这些……从哪里来”等对单次会话作出反应的标题来代替稳定的信息结构。疑问句标题并非一律禁止；只有当它准确表达长期存在的读者目标，并且即使没有本次会话也会采用同一标题时才适用。

“新增内容”不是默认动作，“恢复完整学习路径”才是修改目标。如果新信息属于另一个内容类型，应移动到对应页面并在当前场景就地提供最小解释和链接，而不是把完整说明嵌入当前教程。

## 每个 Task 的完成检查

Task 完成前逐项检查：

- [ ] 新增或改变的核心概念有中文说明。
- [ ] 核心概念先用肯定句说明职责、消费者和产生的结果，再说明表示形式或限制。
- [ ] 阶段性限制按“当前能力 → 可观察后果 → 后续责任”说明，没有把字段增删或评审动作写进正式叙事。
- [ ] 解释某种数据结构“为什么这样设计”前，已经先展示读者理解理由所需的整体形状、字段分组和关系。
- [ ] 规范化状态、ID 表或引用数组至少有一个小型 JSON 结构示例；关系图没有被用来替代实际存储形状。
- [ ] 正式文档只呈现当前有效设计；已经彻底移除的名称、字段和方案没有作为修改过程残留。
- [ ] “已验证”“受支持”“安全”等结论写明责任方、验证证据和消费方，不把调用者自报字段描述成系统保证。
- [ ] 概念、公共 API、状态、关系和模型能力在首次语义使用前已经通过读者基础、就地定义、前置页面或权威链接解决。
- [ ] 标题、正文、代码、图表、表格和 Demo 中没有抢先使用尚未解决的学习依赖。
- [ ] 复合表达已拆成原子依赖检查；不存在用多个英文名词互相解释的情况。
- [ ] 页面首段没有连续堆叠两个以上尚未解释的英文术语。
- [ ] 借用的外部术语有第一方来源，并说明 Tiny Robot 是否改变了它的语义。
- [ ] 项目自定义术语明确标记为项目定义，不把相似外部用法写成标准。
- [ ] 快速开始只引入当前学习阶段所需的最小概念，后续能力的名词留到对应模块解释。
- [ ] 页面已经明确主要内容类型和唯一读者目标，并按该类型的结构约束组织，没有机械复制规范标题。
- [ ] 页面正文在跳过任意或全部 Demo 后仍能独立说明与目标相关的输入、结果或精确信息。
- [ ] 页面包含多个 Demo 时，每个 Demo 都有单一局部观察目标和明确角色；引入新业务目标、架构层或前置模块的扩展 Demo 已拆页。
- [ ] 会话反馈已经转换为明确的文档问题，没有照搬问句、回答顺序或讨论上下文。
- [ ] 修改前已复核页面职责、主要学习目标、提纲和上下游关系；追加章节确实比重写、合并、移动、拆分、删除或链接更合适。
- [ ] 修改后已从页面开头通读到受影响的下一模块，没有问答接缝、重复解释或新的顺序跳跃。
- [ ] 每个进入评审的 Task 已评估其学习路径影响，并为新增能力提供就地中文说明、设计依据和验证证据入口。
- [ ] ADR、契约和临时计划的链接性质已明确标注，读者不会把解释页或计划误认为正式契约。
- [ ] 首页、顶栏和侧栏入口以读者想完成的任务命名，而不是以内部内容分类命名。
- [ ] 公共符号有简洁英文 TSDoc，且没有重复教程内容。
- [ ] 新增关系、边界或生命周期时，有一张聚焦单一问题的 Mermaid 图。
- [ ] 生命周期文档区分不同实体各自的终止事实；阶段性能力不能表达某种流程时，明确其可观察限制和负责扩展的架构层。
- [ ] 所属学习模块已走通最小正常场景，并在本页或相邻页面覆盖一个能纠正核心误解的真实边界。
- [ ] 关键示例映射到公共 API 类型检查或永久回归测试。
- [ ] `docs:check` 零 warning。
- [ ] `docs-next` 构建成功。
- [ ] 内部链接有效。
- [ ] 最终报告列出已覆盖内容与仍未覆盖的风险。

某项确实不适用时，最终报告必须写明原因。例如“只修改拼写，没有新增关系，因此不需要 Mermaid 图”，不能直接跳过。

## 图例规则

一张图只回答一个问题：

- 分层图回答“职责在哪里”；
- 流程图回答“数据按什么顺序流动”；
- 实体关系图回答“谁拥有谁”；
- 状态图回答“允许哪些状态转换”；
- 安全边界图回答“什么数据必须停在哪里”。

如果一张图需要同时解释上述多个问题，应拆成多张图，并在正文中用链接串联。节点文字优先使用短中文，代码标识符保留英文。

## 示例规则

示例必须服务一个明确的学习目标，并放在读者刚获得所需前置概念的位置。局部示例就地解释单个概念；跨概念示例紧跟它最后一个前置概念，不能统一堆放到学习路径末尾。

示例必须说明它代表的是现行契约还是尚未实现的后续设计，并回答：

1. 输入或起始状态是什么；
2. 读者要解决什么问题；
3. 发生了哪些公共可观察变化；
4. 最终消费者读取什么；
5. 哪个关键边界或失败情况值得验证；
6. 哪个类型检查或永久测试保护了这个示例。

安全边界确实依赖某项数据缺席时，示例可以明确说明该数据不会出现；不能为了记录开发过程中删过什么而罗列否定项。

尚未由测试保护的评审示例必须标记“示意，不可复制为当前 API”。设计批准后，要么增加对应验证，要么删除该示例。

独立示例页只用于串联多个已经学过的概念。概念首次出现时仍需就地提供最小片段，不能要求读者跳到独立示例页后再回来理解正文。顶栏可以提供示例索引，但示例索引不能替代主学习路径中的就近入口。

## 入口与学习路径规则

首页主行动、顶栏和侧栏首先回答“读者接下来能做什么”。入口名称应使用“快速开始”“理解状态范围”“查看 API”等行动或目标，避免使用“术语”“资料”“其他”等内部内容分类。

基础术语应融入快速开始的具体场景，在第一次使用前解释。除非需要提供完整的字母索引，否则不要让独立术语表承担新读者的主要入口职责。

快速开始至少应包含：

1. 读完后能获得什么；
2. 一个无需领域背景的具体场景；
3. 理解后续页面所需的最小概念集；
4. 按读者目标选择的下一步链接。

快速开始的页面标题和首段必须让第一次进入项目的读者知道要完成什么，以及负责这项工作的核心对象是什么。不得先在标题、章节名或代码中使用未定义的内部对象，再到后文补充其职责。

通用的页面末尾链接不能替代模块内导航。读者理解完一个学习模块后，必须能够在当前章节直接进入它的设计依据、验证证据和主线下一步。

学习路径中的主入口不得使用 `Task 3`、`Task 8` 等实施编号命名。Task 编号可以出现在贡献者或评审材料中，用来追踪实现范围；面对学习者的入口必须使用能力、问题或读者目标命名。

首页应同时提供：

- 一条从零开始的主学习路径；
- 按目标查找操作指南和参考资料的入口；
- 对学习者、集成者和维护者分别适用的起点。

侧栏中，串联场景应插入其最后一个前置概念之后。单独的“示例”分组可以作为索引保留，但不能是这些场景在主导航中的唯一位置。

## 学习依赖闭包

本节约束承担连续学习或渐进解释职责的页面。ADR、契约和 API 参考等按需查询材料应在自身职责范围内保持可独立核对：必要术语可以就地简要定义或链接稳定权威来源，但不通过“阅读前先完成某教程”转移理解责任。

渐进式阅读检查的对象不是狭义“术语”，而是读者继续理解当前内容所依赖的全部知识。以下内容都属于学习依赖：

- 领域概念、项目专用术语、缩写和协议；
- 公共 API、方法、参数、返回结果和可观察副作用；
- 状态、生命周期、状态转换和终止条件；
- 对象之间的所有权、基数、时序和约束关系；
- 架构角色、责任边界和扩展点；
- 模型或 Provider 能力及其业务含义；
- 代码、图表、表格和 Demo 中需要理解的标签。

“首次语义使用”是读者第一次必须理解某项学习依赖才能继续阅读的位置。页面标题、章节标题、导语、正文、代码、注释、图表节点、表格、Demo 控件、状态和输出都在检查范围内。代码、图表和 Demo 可以帮助观察已经建立的概念，但不能承担项目概念或公共 API 的首次介绍。

每项学习依赖必须在首次语义使用之前通过以下一种方式解决：

1. 它属于页面开头明确声明的目标读者基础；
2. 当前页面在使用前给出足以完成当前任务的最小定义；
3. 主学习路径中的前置页面已经介绍它，当前页面在使用前声明并链接该前置页面；
4. 参考资料等非线性页面在使用前链接到稳定的权威定义。

出现在首次语义使用之后的解释或链接不满足这项规则。“常见开发者都知道”也不能代替读者基础声明。页面可以假设 TypeScript、Promise 或 HTTP 等通用知识，但必须先确定目标读者；Conversation、Run、Model Step、Ingress Guard 等项目概念永远不能仅凭常识假设。

最小定义根据依赖类型回答不同问题：

| 依赖类型 | 首次使用前至少说明                                         |
| -------- | ---------------------------------------------------------- |
| 概念     | 它表示什么、为什么存在、与当前任务有什么关系               |
| 公共 API | 它解决什么问题、主要输入、返回值或副作用、从哪里观察结果   |
| 状态     | 状态属于谁、何时进入、业务上可以据此判断什么               |
| 关系     | 两端对象是谁，以及所有权、基数、顺序或约束是什么           |
| 模型能力 | 能力由谁提供、会产生什么内容或行为、与最终业务结果有何区别 |

复合表达必须拆成原子依赖逐项检查。例如“单 Model Step 的 text/reasoning Run”同时依赖 Run、Step、Model Step、text、reasoning 以及 Run 与 Step 的关系；不能把整句话当成一个术语用括号带过。应先让读者知道：Run 是一次回答尝试，Step 是其中的一次执行阶段，Model Step 是调用模型并接收输出的阶段；`text` 是面向用户的回答内容，`reasoning` 是部分模型能够提供、与最终回答分开的中间推理内容。随后才能说明当前一次 `send()` 只创建一个 Model Step。

公共 API 也按相同规则审查。快速开始不能先给出 `runtime.createConversation()` 或 `selectConversation()` 的调用，再到代码后解释它们。示例前应先说明：前者创建并返回一个用于发送消息的 Conversation 入口；后者接收当前 Snapshot 和 Conversation ID，返回适合界面读取的会话视图。精确签名和全部选项仍由 API 参考承担。

页面审查必须维护“首次使用清单”，逐项记录学习依赖、首次语义使用位置、满足方式和权威定义。清单是评审证据，不写入学习正文。单页通过条件是未解决依赖为零；模块通过条件还包括跨页面依赖无环，主学习路径不要求读者跳到后续页面补齐当前页面的前置知识。

例如不要直接写“协调一次 Run 并归约 Snapshot”，应先写“推进一次回答尝试（Run），再根据已确认事实更新当前状态（Snapshot）”。缩写、英文名词、代码标识符和架构角色不能互相充当解释。

## 正向职责优先

解释一个概念时，首先回答它为什么存在：

1. 它代表或负责什么；
2. 谁创建、拥有或消费它；
3. 它产生什么领域结果或公共可观察结果。

“可序列化”“不可变”“安全”等性质是表示形式或约束，不能代替职责。例如 `SendCommand` 应先解释为“请求 Runtime 在指定 Conversation 中记录用户输入并创建新的 Turn 和 Run”，然后再说明它使用普通数据表示。

否定说明只用于澄清与该职责直接相关的常见误解或风险边界。读者询问“它用来做什么”时，AI 必须补齐正向职责；不得通过继续罗列“它不是什么”“它不能做什么”来回避缺失的定义。

当一次评审疑问暴露出职责未定义时，应同步检查概念页、`CONTEXT.md` 和公共 TSDoc。约束文档可以保留安全性 `MUST NOT`，但解释文档必须先让读者知道约束保护的职责是什么。

## 能力边界与开发日志

阶段性能力不足属于当前有效设计，必须在会影响使用方式、可观察行为或安全判断时明确说明。说明顺序是：

1. 当前能力能够完成什么；
2. 超出能力时，消费者会观察到什么结果；
3. 已确定时，由哪个后续能力或架构层补齐。

开发日志描述的是设计如何从旧状态变成当前状态，例如删除了哪个字段、评审时否决了哪个方案、实现过程中曾使用什么临时类型。除迁移指南、changelog、`@deprecated` 说明和 ADR 决策理由外，这些内容不得进入概念页、快速开始、公共 TSDoc 或现行契约说明。

判断一句限制说明是否应保留时，先忽略本次修改和评审背景，再问：

- 它是否改变消费者对当前输入、输出、生命周期、错误或安全边界的理解？
- 它是否说明一个真实存在的能力缺口及其可观察后果？
- 它是否为后续能力划定必要且仍有效的责任边界？

任一问题为“是”时，可以保留，但应使用当前设计语言。全部为“否”时，它只是修改过程残留，应删除。

推荐写法：

> 当前 reducer 在同一个 Event 中结束最后一个 Step 和 Run，因此不能表示“Step 已结束而 Run 仍为 active”。多 Step 执行通过独立的 Step 终止事实扩展这个生命周期。

不推荐写法：

> 这次没有实现 `step-terminated`，也不会使用之前讨论过的 `legacyStepStatus` 字段。

前者说明当前能力、可观察限制和后续责任；后者只有知道修改历史才有意义。不要为了证明某项内容已经删除，而在正式文档中继续点名它。

## 只呈现当前有效设计

架构说明、概念页、契约、公共 TSDoc 和仍在执行的实施计划都应让读者直接看到当前有效设计，不应写成修改记录。设计调整完成后，用正向职责、数据关系和验证方式描述最终结果，不保留“原来有什么”“这次删掉了什么”或围绕旧名称展开的解释。

一个公共名称、字段或方案已经彻底移除，且不存在兼容期时，应同时满足：

1. 源码、测试、示例和 fixture 不再引用它；
2. 概念说明、契约、ADR 和实施计划使用最终设计语言；
3. TypeDoc、VitePress 等生成产物重新生成后不含残留；
4. 永久测试通过肯定方式保护当前允许的契约，例如校验完整允许集合，而不是只断言某个旧字段不存在。

历史信息只在读者确实需要迁移时进入 changelog、迁移指南或 `@deprecated` 说明；具有长期架构意义的取舍可以保留在 ADR 的决策理由中，但正文仍应使用当前概念，不能依赖已经失效的名称。内部执行日志可以记录验证过程，但不能被当成概念说明或正式设计依据。

## 声明、证据与责任

文档使用“已验证”“受支持”“安全”“兼容”等结论时，必须给出完整责任链：谁对结论负责、什么证据建立结论、哪个组件据此做什么决定。一个由调用者或扩展实现自行填写的字段只能表达声明；除非系统存在独立验证机制，否则不能把它写成 Runtime 已经证明的事实。

评审公共字段时还要检查它是否真正改变消费者行为。如果一个字段只重复上游实现本来就必须承担的准入责任，并且消费者无法独立验证它，应优先把责任放回拥有证据的一层，而不是把自报标签复制到 Domain Event、Run 或 Snapshot。

## 命名来源规则

每个架构名词必须归入以下一类：

1. **直接采用**：来自固定外部规范或依赖，必须记录第一方来源、版本和本项目允许子集；
2. **借鉴模式**：借用成熟概念，必须说明保留了什么含义、改变了什么含义；
3. **项目定义**：由 Tiny Robot 规定边界，必须明确写出“项目定义”，外部同名用法只能作为比较。

来源优先使用规范维护者、依赖项目或平台提供方的官方文档和源码。二手文章只能补充解释，不能作为公共契约的唯一依据。

来源可以紧邻首次解释，也可以集中维护在“命名来源与项目定义”页面，但概念页必须能够到达它。外部资料与项目语义冲突时，项目内已批准契约和 `CONTEXT.md` 优先。

## 按能力渐进披露

快速开始和导航应按照已经可用的能力及其认知前置关系逐步引入概念：

- 当前可用能力的输入、输出和验收行为决定本阶段的最小词汇；
- 尚未进入当前学习阶段的内部组件不能以“先了解全貌”为理由提前堆入快速开始；
- 总览必须提及未来链路时，应标记为后续能力，并在第一次出现时给出一句直白解释；
- 新能力进入评审时，把必要术语、来源和示例放到具有正确前置关系的位置，而不是简单追加到文档末尾。

## 实现 Task 与文档闭环

每个进入评审的实现 Task 都必须检查它对学习路径的影响，但实现 Task 不直接决定页面分类。维护者需要回答：

1. 它是否引入了读者可观察的新能力、概念或边界；
2. 新内容依赖读者已经理解哪些模块；
3. 它应扩展现有学习模块，还是形成新的模块或操作指南；
4. 是否需要一个新的端到端场景来串联多个既有概念；
5. 对应 API 参考、ADR、契约和永久测试如何提供证据。

面向学习者的闭环按以下层级组织：

1. **场景与中文说明**：解释问题、职责、关系、生命周期和可观察结果；
2. **设计依据**：按需链接已接受的 ADR 和已批准的契约；
3. **API 与验证证据**：链接公共 API、可运行示例或保护该行为的永久测试说明。

实施计划只属于贡献者和评审工作流。需要追踪范围时，应从贡献者页面进入计划中的对应 Task；快速开始、概念页和场景页不得要求普通读者理解 Task 编号，也不得把临时实施计划当作学习依据。

ADR 和契约链接必须能够从生成的网站直接打开，不能只显示仓库文件路径。为了避免复制长期设计文档，`docs-next` 应通过只读 include 页面渲染 `docs/architecture/`、`docs/adr/` 和 `docs/contracts/` 中的原文；权威内容仍只在原文件维护。

权威源文件不得反向依赖 `/concepts/...`、`/guide/...` 等文档站根路径，也不得承担文档站的学习导航。权威文档确需互相引用时使用仓库相对路径，并同时验证源码阅读与 include 渲染；学习页面进入 ADR、契约或架构文档时，链接对应的 `docs-next` 展示页。

实施计划不是长期设计依据。只有计划仍属于活动工作流时才可从贡献者或评审入口暴露；计划删除或被替代时，必须同时删除或更新 include 页面和链接。页面末尾可以提供深入参考，但不能用一个通用链接列表代替每个学习模块的就地闭环。

如果一个 Task 同时改变多个彼此独立的读者目标、安全决策或生命周期，它可能需要拆分实现 Task；如果只是因为共享内部机制而同时修改多个概念，则可以保持一个实现 Task，但必须拆成不同学习模块。反过来，一个端到端场景依赖多个 Task 时，应等前置能力具备后再提供完整教程，不要复制成多个不完整版本。

## 教学结构检查

新增或调整学习内容时，除事实正确性外，还必须检查：

- 页面是否先确定唯一主要类型和读者目标，再选择与该类型匹配的信息顺序；
- 教程是否从业务场景和最小正常结果建立经验，操作指南是否围绕完成条件组织，原理说明是否解释关系与不变量，参考资料是否保持精确和可检索；
- 每篇页面是否只有一个主要目标；每篇教程是否只承担一个主要学习跃迁；
- 新术语是否在实际需要它的位置首次出现；
- 教程和操作指南的正常路径是否在边界、变体和扩展之前完成；
- 示例是否紧邻其前置概念，而不是集中放到末尾；
- 页面能否按自身职责独立成立；需要学习顺序的页面是否说明必要前置、结果和下一步；ADR、契约与 API 参考是否避免伪造教程顺序；
- 跳过任意或全部 Demo 后正文是否仍然成立；多个 Demo 是否各有单一角色并沿同一目标渐进展开；
- 不知道最近会话内容的读者，能否理解每个章节为什么出现在当前位置；
- 新增标题是否表达稳定的读者目标，而不是复述一次追问；
- 页面标题和章节标题单独组成目录时，是否仍能表达任务、主题和推进顺序，而不是作者的叙事动作；
- 面向新读者的入口是否在标题或首段依赖尚未定义的项目术语；任务型标题是否表达具体动作或结果，概念型标题是否表达明确主题；
- 本次修改是否恢复了整页主线，而不是只让新增段落局部正确；
- 实现 Task 编号、评审动作和字段修改历史是否泄漏进学习叙事；
- 扩展说明是否指出稳定扩展点、责任层和不变量，而不是罗列猜测性的未来字段；
- 扩展 Demo 是否仍属于当前目标；如果引入新的业务目标、架构层或前置模块，是否已经拆页；
- 一个实现 Task 覆盖多个概念时，文档是否仍按读者目标拆分；
- 多个实现 Task 共同形成一个场景时，是否提供了一个不重复、可验证的整合入口。

具体评审步骤、问题分类、通过条件和可复制记录见[学习文档评审指南](./learning-document-review.md)。规范决定“必须满足什么”，评审指南说明“怎样验证它”。

## 方法来源

本项目借鉴以下方法，但以项目内已批准契约和实际读者目标为准：

- [Diátaxis](https://www.diataxis.fr/)：区分学习教程、操作指南、参考资料和原理说明的用户需求；
- [Diátaxis Tutorials](https://www.diataxis.fr/tutorials/)：通过具体行动、早期结果、小步推进和连续预期建立学习体验；
- [Diátaxis How-to guides](https://www.diataxis.fr/how-to-guides/)：围绕真实目标和问题组织操作指引；
- [Google Technical Writing：Organizing large documents](https://developers.google.com/tech-writing/two/large-docs)：在需要信息的位置引入概念，从简单示例逐步增加复杂度，并交替使用概念说明和实践；
- [Google Developer Documentation Style Guide：Jargon](https://developers.google.com/style/jargon)：必要术语在首次出现时清楚定义，或链接到可信定义；
- [Google Technical Writing：Words](https://developers.google.com/tech-writing/one/words)：新词或陌生词应在使用处解释或链接，并在全文保持一致；
- [Google Developer Documentation Style Guide：Headings and titles](https://developers.google.com/style/headings)：页面标题反映主要目的，任务型标题使用动作短语，概念型标题使用名词短语，并保持层级和可扫描性；
- [Microsoft Writing Style Guide：Word choice checklist](https://learn.microsoft.com/en-us/style-guide/checklists/word-choice-checklist)：根据目标读者在上下文中定义技术术语，使用简单且一致的词汇；
- [Microsoft Writing Style Guide：Headings](https://learn.microsoft.com/en-us/style-guide/scannable-content/headings)：标题应组成清晰提纲，突出读者要完成或需要知道的内容，并在同层级保持平行结构。

## AI 检查方法

AI 在结束一个 Task 前不能只搜索缺失的 TSDoc。还必须对照改动回答：

- 本次会话反馈暴露的根因是什么，最终修改是否解决了根因而不是复述回答；
- 修改前是否明确了目标页面的主要内容类型、唯一读者目标、提纲位置和上下游关系；
- 页面是否按对应类型的信息顺序展开，而不是把共享规范当成固定标题模板；
- 页面标题是否直接表达主要目的；把全部标题单独列出后，是否仍是一份读者可理解的内容提纲；
- 面向新读者的入口是否在定义职责前就要求读者理解内部术语；
- 任务型标题是否写成具体动作或结果，概念型标题是否写成明确主题，并避免“先看……”“这个示例……”等作者叙事；
- 是否默认追加了标题或段落；如果是，为什么重写、合并、移动、拆分、删除或链接都不合适；
- 不知道本次会话的读者，能否理解新增内容为何出现以及它与前后文的关系；
- 从页面开头重新阅读后，是否仍只有一个主要目标，并且开头承诺、正文和适用的下一步一致；
- 跳过任意或全部 Demo 后，正文是否仍能建立完整结论；
- 页面包含多个 Demo 时，它们分别属于快速、能力、边界还是扩展用途，是否各自只有一个局部观察目标；
- 扩展 Demo 是否引入了新的主要业务目标、架构层或前置模块；如果是，是否已经拆成后续页面；
- 新增名词是否在 `CONTEXT.md` 有一致含义；
- 每个核心概念是否先说明职责、消费者和结果，而不是先罗列性质或排除项；
- 文档在解释结构取舍前，是否先展示了读者无需查看源码也能理解的整体结构和关系；
- 规范化状态是否给出了能看出表 key、实体 ID 和引用字段关系的 JSON 示例，而不是只画实体关系图；
- 面对读者疑问时，修改是否补齐了缺失的正向定义，而不是只增加新的否定断言；
- 阶段性限制是否说明当前能力、可观察后果和后续责任，而不是枚举本次删除、延期或未采用的字段与方案；
- 正式文档是否只描述当前有效设计，而不是叙述字段增删和评审过程；
- 已彻底移除且没有兼容义务的名称是否已从源码、测试、说明和重新生成的站点中清零；永久测试是否改为保护当前允许的完整契约；
- 文档中的验证或支持结论是否说明了责任方、证据和消费决策；自报字段是否被误写成系统保证；
- 是否已列出页面的学习依赖，并检查标题、导语、正文、代码、图表、表格和 Demo 中的首次语义使用；
- ADR、契约和架构源文件是否混入教程前置要求或文档站根路径；学习导航是否留在 `docs-next` 展示层；
- 每个公共 API 在示例代码前是否说明用途、主要输入、返回值或副作用以及结果读取位置；
- 每个状态、关系和模型能力在首次使用前是否说明其业务含义，而不是只出现类型名或字段名；
- 复合表达是否拆成原子依赖逐项检查，且每项都已由读者基础、就地定义、前置页面或权威链接解决；
- 读者是否无需跳读后文才能理解当前内容，首次使用清单中的未解决依赖是否为零；
- 相邻页面的学习依赖是否形成环路，或要求读者跳到后续页面补课；
- 页面第一段是否堆叠了尚未定义的英文名词；
- 每个借用名词是否有第一方来源和项目差异说明；
- 每个项目自定义名词是否被误写成行业标准；
- 快速开始是否只包含当前学习阶段的必要词汇；
- 每个进入评审的 Task 是否评估了学习路径影响，并形成“场景与中文说明 → ADR/契约 → API 与验证证据”的可点击闭环；
- 是否把临时计划错误地当成长期设计依据，或留下已经失效的计划链接；
- 首页和导航名称是否描述读者目标，而不是暴露文档内部分类；
- 快速开始是否把基础概念放进具体场景，而不是只罗列词汇；
- 新增字段是否改变所有权、范围、生命周期或安全边界；
- 一个 Event 同时改变多个实体状态时，文档是否说明这是领域上的一个事实还是当前阶段的合并实现，并明确多阶段流程是否可表达；
- 读者是否能从中文文档找到至少一个具体场景；
- 图中关系是否与 TypeScript 类型、契约和永久测试一致；
- 文档是否把未来计划写成现行事实；
- 示例中的每个公共字段是否仍能通过类型检查。

发现无法判断的公共语义时，应停止实现并请求维护者决策，而不是通过模糊注释隐藏问题。
