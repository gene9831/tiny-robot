# 公共组件契约规范

状态：设计草案。基础要求沿用[组件设计基础](./component-design-foundations.md)；推荐规则尚待确认，组件级选择与公共待决问题分别列明。

## 1. 目的与适用范围

本文帮助开发人员和 AI 明确一个组件接收什么、谁决定当前状态、一次操作请求什么，以及哪些结果已经发生。重点是输入声明、状态所有权、事件及可选的命令式接口，适用于独立于具体产品、面向浏览器的通用组件。

公共契约负责约束各组件共有的语义；组件级契约负责选择具体值域、状态维度、操作、事件与验收条件。开发人员据此设计、集成和评审组件，AI 据此实现和验证行为。本文不定义描述文件格式、Schema、内核接口或框架适配代码，也不表示相关能力已经实现。

本文使用三种约束层级：

- **基础要求**：沿用组件设计基础中的职责与行为原则；“必须”“不能”仅用于这些要求及其直接约束。
- **推荐规则**：建议统一采用的默认策略，尚未确认为公共标准。组件采用其他策略时，应说明场景、差异与验收条件。
- **组件须声明的选择**：存在多种合理方案，由具体契约明确；公共规范尚未决定的统一策略见第 9 节。

所有示例接口名均为框架无关的语义示意，不是已实现 API，也不要求所有组件开放相同的状态、事件或方法。React、Vue 等框架可以采用各自的属性和事件语法，但需要保留声明的公共语义。整体职责与开发体系见[架构总览](./cross-framework-component-architecture.md)。

## 2. 输入的范围与分类

组件既接收应用提供的声明式输入，也响应用户操作、命令调用及平台观察。设计契约时，先说明声明式输入采用什么形式，再判断其中的属性承担什么角色，最后按状态维度确定所有权。这三个问题分别描述接口形式、声明用途和状态权威来源，不能合并成一张互斥分类表。

### 2.1 声明式输入的语义形式

以下是本架构建议采用的逻辑声明分类，用于组织契约，不是所有框架实际传参语法的互斥全集，也不预先确定描述文件字段。

| 形式 | 含义与示例 | 契约需要说明 |
| --- | --- | --- |
| 属性 | 以具名输入提供数据、配置、状态值或计算扩展，例如 `options`、`disabled`、`value`、`defaultValue`、`formatter` | 类型、用途、缺省与空值、更新影响；涉及状态时另行确定所有权 |
| 内容区域 | 应用向组件声明的呈现位置提供内容或结构，例如 Dialog 正文、Select 选项内容 | 区域含义、默认内容、替换范围、可读取的状态，以及需要保留的事件、引用和无障碍责任 |
| 上下文依赖 | 从声明的作用域读取共享条件，例如语言、方向、主题或上层组件提供的状态值 | 提供者、作用域、缺失时的行为、更新规则及与其他入口的覆盖关系 |

每条逻辑声明按其用途归入一种形式；框架接入语法可以重叠。React 的 `children` 本身是 prop，向某个呈现位置提供内容的 render prop 也通过 prop 传递，但契约可以将它们声明为内容区域；Vue 插槽和 Angular 内容投影可以承接相应语义。跨框架验收检查内容、可定制范围与行为责任，不要求物理传参方式相同。参见 [React 的 children 说明](https://react.dev/learn/passing-props-to-a-component)、[Vue 插槽](https://vuejs.org/guide/components/slots.html)和 [Angular 内容投影](https://angular.dev/guide/components/content-projection)。

函数类型不能决定分类。`formatter` 若把值转换成显示文本，属于属性形式的计算扩展，需要遵守纯计算约束；若渲染函数用于提供选项结构，则按内容区域说明。`onChange` 一类回调在 React 中虽然通过 prop 传入，语义上用于绑定组件输出事件，其触发与载荷应在事件契约中说明，不能因为它是函数就归为计算或内容扩展。

### 2.2 属性的角色

属性角色按声明用途区分，不能仅凭类型或名称判断。布尔属性 `disabled` 可以是配置，布尔属性 `open` 可以为打开状态提供受控值；后者是否受控仍取决于该状态的识别规则。

| 角色 | 含义 | 示例 | 契约需要说明 |
| --- | --- | --- | --- |
| 普通数据与配置 | 提供呈现数据、可用范围、行为条件或计算策略 | `options`、`disabled`、`formatter` | 类型、缺省行为、更新影响、只读约束及计算扩展的纯度 |
| 受控值 | 应用为某个状态维度提供当前权威值 | `value`、`open` | 对应状态、如何识别受控、合法值域与同步规则 |
| 非受控初始化值 | 在非受控初始化时确定起点 | `defaultValue`、`defaultOpen` | 何时读取、后续变化与重置的关系 |

同一字段按其声明用途选择角色：为可交互状态提供当前权威值时归为受控值，仅用于非受控起点时归为初始化值，其他只读数据、配置或计算策略归为普通数据与配置。复合对象包含不同用途的字段时，应分别说明这些字段的角色，不能因为共用一个对象属性就把它们视为同一种语义。

配置属性的缺省值与非受控初始化值不同。例如，`disabled` 未提供时采用 `false` 是配置的缺省行为；`defaultValue="A"` 是非受控文本状态的初始化输入。不能因为某属性有缺省值，就为它机械地增加受控与非受控两套接口。

输入对象及嵌套数据按只读契约使用。Select 根据 `options` 筛选结果时，不能原地修改应用的选项数组；应用更新选项也不必然表示选中值已变化。选中项被移除后的保留、清空、回退或修正请求，需要在该组件契约中另行声明。

**推荐规则：非受控初始化值仅用于初始化。** 后续更改 `defaultValue` 等输入不自动覆盖最终用户已经完成的编辑。应用若要持续决定当前值，应采用受控输入；若要重新开始，应使用组件明确支持的重置或重新创建机制。这样可避免应用重渲染时意外清除编辑，但需要额外声明重置目标。

**推荐规则：受控值决定有效值。** 当某个状态已按契约识别为受控时，同时提供初始化值不应使初始化值成为第二权威来源。建议以受控输入为准；是否接受这一组合、是否给出诊断，由契约明确。该规则不替代受控识别条件，也不规定 `undefined` 或 `null` 的跨框架含义。

### 2.3 来源与覆盖关系

上下文说明输入从哪里取得，不决定状态由谁拥有。上下文可以提供普通配置，也可以提供某个状态的权威值；后者仍需按第 3 节声明所有权、更新请求与同步规则。Vue 的 [Provide / Inject](https://vuejs.org/guide/components/provide-inject.html)提供了跨层传递依赖的机制，但该机制本身不替组件决定公共控制契约。

同一设置若既可通过属性传入，也可由上下文提供，应分别声明两个入口，并明确优先级、空值含义和作用域变化后的行为。例如，日期组件可以选择“显式语言属性优先，其次读取语言上下文，均缺失时使用组件声明的缺省语言”。这是组件须声明的选择，不能从“属性”或“上下文”自动推导统一优先级。

### 2.4 声明变化与运行时触发

声明式输入描述组件当前接收的条件；用户操作、命令调用、平台观察与异步完成描述某次触发。它们可以共同影响状态，但触发一次不等于应用已经更新了权威值。

| 场景 | 契约判断 |
| --- | --- |
| 应用更新 Select 的 `options` | 普通数据属性发生外部同步；重新计算筛选结果，选中值失效时另按声明规则处理 |
| 应用提供 Select 的选项渲染函数 | 声明内容区域的定制；函数收到哪些状态、哪些交互责任需要保留，由区域契约说明 |
| 上层语言上下文改变 | 上下文依赖更新；是否覆盖局部语言属性，按入口优先级处理 |
| 最终用户点击选项 B | 用户操作触发选择规则；选中值受控时，候选 B 仍需应用接受 |
| 调用方执行已公开的 `focus()` | 命令式调用触发焦点动作；可用时机及实际结果由方法契约说明 |
| 平台报告尺寸变化或动画完成 | 平台观察或异步结果触发协调；需要验证结果仍有效，并按生命周期规则处理 |

这些场景帮助区分输入形式、更新来源和行为结果；不要求每个组件支持全部入口或触发方式。状态路径见第 4 节，公开方法的可选边界见第 6 节。

## 3. 按状态维度确定所有权

### 3.1 有效值、候选值与内部状态

| 概念 | 定义 | 需要避免的混淆 |
| --- | --- | --- |
| 有效值 | 当前用于组件公共语义与呈现的值；受控时服从应用输入，非受控时服从组件拥有的状态 | 一次修改请求不表示候选值已经生效 |
| 候选值 | 操作希望采用的新值，可能被应用接受、拒绝或转换 | 请求载荷不是下一次有效状态的保证 |
| 内部状态 | 组件拥有并管理的状态；既可包含非受控有效值，也可包含临时交互状态 | “内部”不等于“仅有视觉效果”，也不表示自动公开 |
| 派生状态 | 从权威输入及状态计算的结果，例如过滤项、字符数 | 不再作为可独立修改的第二份事实 |

这些分类描述不同方面，不是互斥的四个容器。非受控选中值既是内部状态，也是该维度的有效值；候选值可以只在一次操作处理中存在，无须保存为长期状态。

受控 Input 若允许编辑草稿，需要额外声明草稿、提交值、输入法组合状态及显示文本之间的关系。草稿不能悄然替代受控有效值。简单 Input 可以不公开草稿；复杂编辑器也不需要把所有选区和历史状态都交给应用管理。

### 3.2 分别确定各状态的所有权

每个状态维度必须有明确的权威来源。受控与非受控按维度定义，不能用一个笼统的“受控组件”推断所有内部行为。

例如，一个 Select 可以采用以下组合；这只是一个契约选择。表中同时列出状态、外部数据与派生结果，以说明它们如何协作，不把“受控”“内部”“应用输入”和“派生”作为同一维度的互斥所有权类别：

| 状态、输入或结果 | 权威来源与维护方式 | 操作与结果 |
| --- | --- | --- |
| 选中值 | 应用受控 | 选择 B 产生候选值；应用回传后成为有效选中值 |
| 展开状态 | 组件非受控 | 打开操作按声明规则更新内部展开状态 |
| 高亮项 | 组件拥有并在内部维护 | 方向键移动高亮；高亮不等于已选中 |
| 选项数据 | 应用提供，组件只读消费 | 组件消费数据，不接管远程查询 |
| 筛选结果 | 从权威输入及状态计算 | 根据选项与搜索条件计算，不独立持有权威副本 |

选中状态受控，不妨碍高亮、按压反馈等内部交互发生；反之，组件内部更新展开状态，也不授权它覆盖应用拥有的选中值。[React 的状态共享说明](https://react.dev/learn/sharing-state-between-components)也按具体状态讨论控制来源，但本文的公共规则仍属于本架构的契约选择。

### 3.3 每个可交互状态的最小说明

组件级契约至少明确以下内容：

1. 状态含义、值域、空值与合法性条件，以及它影响的公共语义。
2. 权威来源；支持受控、非受控中的哪些模式，如何识别，哪些状态不公开控制。
3. 初始化来源，以及默认值后续变化、显式重置和重新创建实例的区别。
4. 用户操作、外部同步和命令分别如何影响有效值、候选值及相关内部状态。
5. 应用拒绝或转换候选值时的呈现和事件；输入失效时的处理。
6. 控制模式是否允许切换；允许时如何交接，不允许时如何诊断。

**推荐规则：关键语义状态优先支持受控，控制模式默认保持稳定。** 选中值、文本和打开状态经常需要与应用协作；高亮、测量结果等不因此强制开放。默认不切换模式可减少权威来源交接问题，但尚不是跨框架强制规则。空值标记和模式切换的具体策略仍需确认。

## 4. 区分四种状态输入路径

同一个值可以经不同路径进入组件，路径决定其语义。下表说明路径存在时的规则，不要求组件开放命令式入口。实现不能仅监测到“某个字段变了”，就统一发出用户修改请求。

| 路径 | 受控状态 | 非受控状态 | 事件边界 |
| --- | --- | --- | --- |
| 初始化 | 从外部权威值建立有效状态 | 从默认值或声明的初始规则建立内部有效状态 | 不能把初始化当作最终用户操作；是否提供初始化通知需声明 |
| 用户操作 | 产生候选值，向应用提出修改请求；有效值仍服从外部输入 | 按交互规则更新内部有效值 | 按契约区分操作意图、修改请求与已发生变化 |
| 外部同步 | 新的权威输入决定有效值 | 配置更新、默认值变化及显式重置分别按契约处理 | 不能因同步又回发同一状态的修改请求，造成更新循环 |
| 命令调用 | 不能绕过应用所有权，按声明语义请求修改或返回结果 | 按声明规则更新内部状态或执行动作 | 明确命令是否产生请求、变化通知或平台结果 |

初始化、外部同步可以引起渲染与派生结果更新；若组件提供覆盖这些来源的有效变化通知，需要明确来源。它们不应被伪装成用户操作。外部输入引发的其他状态协调，例如新选项使高亮失效，也需要独立规则，不能借同步之名悄然修改受控选中值。

## 5. 让事件准确表达发生了什么

### 5.1 四类事件语义

| 语义 | 回答的问题 | 语义示意 | 不能据此推断 |
| --- | --- | --- | --- |
| 操作意图 | 最终用户或调用方希望做什么？ | `confirm`、`submit` | 服务端操作已经成功，或 Dialog 已关闭 |
| 状态修改请求 | 希望哪个状态采用什么候选值？ | `requestValueChange`、`requestOpenChange` | 候选值已成为有效值 |
| 有效状态变化通知 | 哪个有效状态已经变化？ | `valueChanged`、`openChanged` | 变化一定来自最终用户，或平台动画已经完成 |
| 平台动作结果 | 哪个平台动作实际完成或失败？ | 复制结果、焦点动作结果 | 应用数据已经保存或提交 |

这是语义分类，不要求每个组件提供四套事件。状态订阅也不自动等于上述对外事件；它可能只通知适配器重新读取快照，具体协议另文定义。

事件必须如实区分请求与结果。受控 Dialog 收到关闭请求而仍然打开时，不能报告“有效打开状态已变为 false”；外部传入 `open=false` 后，是否还有退出动画、动画何时完成，则由平台与生命周期契约说明。

### 5.2 推荐的通知策略

建议受控状态提供修改请求；非受控状态在内部有效值改变后提供变化通知。若组件希望应用观察所有来源的有效变化，可以额外提供覆盖用户操作、命令和外部同步的变化通知，并标明来源。是否提供这些通知由组件契约确定，不要求所有事件同时存在。

请求与变化通知应保持可区分的含义。框架绑定可能把其中一类映射为 `update`、`Change` 或回调；不能仅凭名称推断它代表请求还是结果。以 Vue 为例，[组件 `v-model` 文档](https://vuejs.org/guide/components/v-model.html)说明了属性与更新事件的映射，并提示默认值可能导致父子不同步；该机制不能代替组件自身的有效值与候选值定义。

建议请求载荷包含候选值，并在应用需要判断时包含请求前的有效值和触发原因。变化通知则说明实际生效的值，必要时包含前值与来源。原因可表达选择项、输入、清空、关闭按钮或命令等语义；具体字段名、值域及是否携带原始浏览器事件，由组件契约决定。

使用“已变化”语义的通知需要声明相等性判断。例如 Select 的对象值按引用、键还是自定义比较判断，会影响相同语义值是否被视为变化。请求表达一次尝试，即使有效值未变也可能有意义；是否合并重复候选请求、有效值相等是否也抑制请求，需要单独确定。

### 5.3 每个事件的声明内容

事件说明至少覆盖语义类别、触发条件、载荷、适用模式、来源、取消效果及必要的先后关系。对于相互独立的状态，不应凭一次实现的回调顺序建立公共承诺。

应用处理受控请求时可以立即、延后、拒绝或转换候选值。组件应依照后续收到的权威输入确定有效值；没有回传不表示接受。延后接受时是否保留编辑草稿、显示等待状态或允许继续操作，由具体交互契约确定。请求与外部回传的因果对应方式也需要按场景声明，不能假定“下一次输入更新”一定是在回应最近请求。

## 6. 可选的公开方法与命令

### 6.1 何时提供命令式接口

公开方法与命令是可选接口。组件仅提供属性、内容区域和事件即可满足使用场景时，无须为了契约完整性额外暴露方法。共享内核用于处理交互的命令也不自动成为组件公共 API；是否公开、公开什么能力及各框架如何接入，需要分别声明。

**推荐规则：能够通过状态表达的需求，优先采用声明式输入。** 例如，应用持续决定 Dialog 是否打开时，优先用 `open` 一类状态属性表达。聚焦、滚动到指定位置、设置文本选区等动作难以仅用持续状态完整表达，可以按场景提供 `focus()`、`scrollTo()` 或选区方法。这样可减少属性与方法同时竞争同一状态的更新权，但需要为命令式动作额外定义可用时机与失败结果。

[React 的 useImperativeHandle 说明](https://react.dev/reference/react/useImperativeHandle)建议将命令式句柄用于焦点、滚动和文本选区等行为，并以 Modal 为例建议优先用属性表达打开状态；[Vue 的组件模板引用说明](https://vuejs.org/guide/essentials/template-refs.html#ref-on-component)也建议优先采用 props 与 emits，仅在必要时通过组件引用调用方法。这些资料支持接口选择的取舍，不构成所有组件共享的方法清单。

### 6.2 选择公开后需要声明的契约

每项公开方法或命令应说明：

- 适用场景、参数与合法值，以及挂载、禁用、退出动画等条件下是否可调用。
- 对有效值、候选值、内部状态及平台行为的影响，受控与非受控时分别如何处理。
- 是否产生修改请求、变化通知或动作结果，以及取消或失败的含义。
- 返回值承诺的是请求已接收、状态已变化还是平台动作已完成。
- 涉及异步时的完成条件、重复调用、失效和组件销毁规则。

**推荐规则：命令与相同用户操作共享状态所有权规则。** 若某个 Dialog 选择公开 `close()`，受控时推荐提出关闭请求，由应用决定是否回传 `open=false`；非受控时可按契约直接改变内部打开状态。该示例仅约束选择公开此方法的组件，不表示所有 Dialog 都应提供 `open()` 或 `close()`。任何公开方法都不能暗中覆盖受控权威值。

方法返回值、命令是否可取消及异步完成条件属于组件级选择；本文不把所有命令统一规定为 Promise，也不决定 `reset()` 的目标。第 7.4 节用选择公开 `close()` 的 Dialog 说明请求与结果的验收边界。

## 7. 用场景验证契约

以下场景采用本草案的推荐策略，描述语义结果，不是可运行代码。状态与呈现结果在实现完成相应输入同步和渲染后观察。简单 Input 不含独立编辑草稿；Select 的选项 A、B 都合法；Dialog 的关闭请求可由应用拒绝。组件选择其他策略时，需要提供对应场景及理由。

### 7.1 Input：受控请求被拒绝或转换

初始条件：有效文本为 `"A"`，来自应用受控输入。最终用户编辑出候选文本 `"Ab"`，组件提出修改请求。

| 应用处理 | 预期有效值与呈现 | 预期事件 | 验收判据 |
| --- | --- | --- | --- |
| 拒绝，继续提供 `"A"` | 有效值仍为 `"A"`，本例呈现 `"A"` | 修改请求携带候选 `"Ab"`；本例没有有效值变化可报告 | 在应用未回传新值时，不把 `"Ab"` 当作已生效文本 |
| 转换后回传 `"AB"` | 有效值与呈现变为 `"AB"` | 原请求仍是 `"Ab"`；若有全来源变化通知，报告 `"A" → "AB"`，来源为外部同步 | 候选值与最终有效值分别可辨，回传不再触发 `"AB"` 的修改请求 |

这里约束的是公共有效值与稳定呈现；浏览器输入接入中的瞬时 DOM、光标和输入法协调，需要在 Input 的具体契约与平台适配中验证，不能由本例推导所有输入控件的编辑时机。

### 7.2 Input：非受控默认值后续变化

初始条件：无受控值，`defaultValue="A"`，采用“仅初始化”建议，且提供内部有效值变化通知。最终用户输入 `"B"` 后，应用把默认值改成 `"C"`。

预期：初始化有效值为 `"A"`；用户输入后有效值成为 `"B"`，变化通知报告实际更新；默认值改为 `"C"` 后，当前有效值继续为 `"B"`，这次默认值更新不产生文本修改请求。应用不处理变化通知，也不会撤销已经完成的内部更新。

验收判据：默认值更新不覆盖已编辑值；重新创建一个只接收 `defaultValue="C"` 的实例时，其初始有效值为 `"C"`。这不推导当前实例的 `reset()` 也必须采用 `"C"`；重置目标另行声明。

### 7.3 Select：外部同步与各状态独立所有权

初始条件：选中值受控为 A；展开状态非受控为关闭；高亮项由组件内部管理。

| 动作 | 预期有效状态 | 预期事件与验收判据 |
| --- | --- | --- |
| 应用直接把选中值改为 B | 有效选中值为 B | 不产生新的选择 B 修改请求；若提供全来源变化通知，来源为外部同步 |
| 最终用户打开面板并把高亮移到 A | 展开为打开，高亮为 A，选中值仍为 B | 打开与高亮的变化不冒充选中值变化 |
| 最终用户确认 A，应用继续提供 B | 产生候选 A，有效选中值仍为 B | 请求载荷为 A；应用拒绝不影响组件按契约管理内部高亮和展开状态 |

验收时分别读取选中、展开和高亮语义，不能用“整个组件受控”要求它们一起停留或变化。确认选择后面板是否关闭、高亮如何协调，需要由 Select 契约选定，本例不作统一规定。

### 7.4 Dialog：关闭请求、有效关闭与平台完成

初始条件：`open=true` 由应用控制；Dialog 处于打开状态；本例的 Dialog 选择公开 `close()`，关闭按钮与该方法均按“提出关闭请求”的建议执行。未公开此方法的 Dialog 只需验收其实际支持的入口。

| 动作或条件 | 预期有效状态 | 预期事件与平台行为 |
| --- | --- | --- |
| 最终用户点击关闭，或调用方执行 `close()` | 仍为打开，等待应用决定 | 提出候选 `open=false` 的请求，区分用户操作与命令来源；不能报告有效状态已关闭 |
| 应用因编辑未保存而拒绝 | 继续打开 | 保持打开状态对应的交互与焦点责任；请求本身不触发关闭后的焦点恢复 |
| 应用接受并回传 `open=false` | 有效打开状态变为关闭 | 若有全来源变化通知，报告实际变化；按关闭契约处理焦点与资源 |
| 声明的退出动画完成 | 有效打开状态仍为关闭 | 若提供动画完成通知，依据实际完成情况输出；不能把它与有效值变化混为一个时刻 |

验收判据：应用拒绝时 Dialog 继续履行打开状态的责任；接受后才执行与有效关闭相应的行为。若契约允许退出期间保留 DOM，需要另行说明可交互性、焦点恢复与资源清理时机，不以 DOM 是否还存在判断有效打开状态。

确认删除也是操作意图。应用可以等待删除成功后再回传关闭状态，也可以保留 Dialog 显示错误；通用 Dialog 不负责执行删除请求。[Radix Dialog 的受控示例](https://www.radix-ui.com/primitives/docs/components/dialog)展示了由外部操作完成后更新打开状态的实践，不构成所有 Dialog 的统一 API。

## 8. 形成可实现、可验收的组件契约

一个可供开发人员或 AI 实现的组件契约，应让读者能沿着“初始条件 → 操作或输入变化 → 有效状态与事件 → 平台结果”判断行为。至少包含：

- 声明式输入的形式、来源与覆盖关系；属性的角色、类型、默认与空值语义，以及更新后的影响。
- 各状态维度的权威来源、可控制范围与派生关系。
- 初始化、用户操作、外部同步，以及已提供命令的规则，含拒绝、转换及输入失效场景。
- 每项事件的语义、载荷、适用模式、取消或失败条件，以及必要的时序承诺；若选择公开方法或命令，再补充对应参数、结果与调用边界。
- 能区分候选值与有效值、请求与结果的验收场景，并说明相关平台观察条件。

这些内容是语义完整性要求，不规定文档模板或机器可读字段。AI 不能从 `value`、`change`、`close` 等名称自行补齐缺失语义；若任务依赖的选择尚未声明，应先确认该选择，而不是借框架默认行为代替公共契约。

## 9. 尚待确认的公共策略

以下问题影响公共一致性，不能仅凭上述示例视为已经定稿：

| 问题 | 当前推进方向 | 仍需确定 |
| --- | --- | --- |
| 受控识别与空值 | 每个可受控维度显式声明 | 未传、`undefined`、`null`、空字符串与空数组的跨框架映射，是否使用统一标记 |
| 默认值与受控值并存 | 推荐受控输入优先，不以默认值补成第二权威来源 | 是否禁止组合、诊断方式与适配差异 |
| 控制模式切换 | 推荐实例内保持稳定 | 是否允许例外，状态交接、诊断与兼容要求 |
| 重置与表单关联 | 推荐默认值仅初始化，不推定重置目标 | 原始默认值、最新默认值或其他目标，以及原生表单 reset 的映射 |
| 事件与通知 | 区分四类语义，推荐来源清晰 | 命名、载荷公共字段、哪些通知必需、相等性和重复候选请求处理 |
| 时序 | 只承诺具体契约需要的因果关系 | 是否统一部分事件顺序、批处理和同步处理请求时的重入规则 |
| 输入失效 | 不让同步悄然覆盖受控所有权 | 哪些情况保留、规范化、回退或请求修正，公共策略与组件策略如何分工 |

相关组件在实现前需要解决其实际依赖的项目，但无需为未开放的状态设计全部模式。快照、订阅与命令接口的发布顺序等内核协议，以及 SSR、水合、焦点与动画的具体规则，继续由对应专题展开。

## 10. 参考边界

本文的状态所有权与职责要求来自[组件设计基础](./component-design-foundations.md)。外部资料帮助核对概念与具体机制，不替代公共设计选择：

- [React：Sharing State Between Components](https://react.dev/learn/sharing-state-between-components)：受控与非受控的相对含义，以及不同状态可以采用不同控制来源。
- [React：input](https://react.dev/reference/react-dom/components/input)：React 原生输入的 `value`、`checked`、默认值与控制模式约束。其原生输入规则不能直接扩大为所有框架和自定义组件的统一约束。
- [Vue：Component v-model](https://vuejs.org/guide/components/v-model.html)：模型属性与更新事件的映射，以及默认值造成父子不同步的风险。
- [Radix Primitives：Dialog](https://www.radix-ui.com/primitives/docs/components/dialog)：`open`、`defaultOpen` 与变更回调的库级接口，以及外部操作完成后控制关闭的示例。

HTML 原生控件、框架对原生控件的接入和自定义组件是不同层次的契约。采用原生元素时需要同时遵守适用的平台行为；不能因为某框架对原生输入限制模式切换，就宣称通用自定义组件只能采用同一策略。
