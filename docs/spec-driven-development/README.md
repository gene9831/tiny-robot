## 适用范围

- 通用 UI 组件及其跨框架开发体系，不绑定具体项目的目录、依赖或现有实现。
- 数据层、专业领域规则及项目改造方案不在当前范围内。
- 当前设计与验证面向浏览器中的 Web 组件及其交互实现；首批采用 Vue、React、Angular 和原生 JavaScript，其他框架可通过适配接入。
- 非浏览器平台仅保留扩展边界，不设计 React Native 等非 DOM 平台的具体实现，也不承诺支持；Web 组件的 SSR 与水合要求仍需确定。

## 常见问题

### 通用组件架构与专业领域能力是什么关系？

通用架构定义组件模型、状态、交互、平台行为与跨框架适配。专业领域规则可以在这些基础上扩展，数据处理及应用流程由外部负责。

详见[总览的目标与范围](./cross-framework-component-architecture.md)。

### 跨框架目标是否只包含 Vue、React、Angular？

目标是通过框架无关的共享内核、统一契约及适配机制接入不同前端框架，并支持原生 JavaScript。首批验证采用浏览器中的 Vue、React、Angular 和原生 JavaScript。

其他框架可以补充面向浏览器的适配和 UI 实现，复用共享行为；具体可用性通过实现和验证确认。首批验证的具体版本、组件和顺序尚未确定。

详见[总览](./cross-framework-component-architecture.md)第 1、4.4、7 节。

### 只面向浏览器，为什么还需要平台交互层？

焦点、测量、滚动和定位等 Web / DOM 行为需要在多个框架间复用。平台交互层集中处理这些环境能力，框架适配器协调元素引用和渲染时机，共享内核负责框架无关的组件行为。平台能力按具体需求定义接口，不提前设计覆盖所有平台的统一抽象，也不要求独立拆包。

框架接入与平台适配分别评估；当前不展开非 DOM 平台的实现设计。

详见[总览](./cross-framework-component-architecture.md)第 3、4.3、4.4 节。

### 内部状态会破坏“确定输入带来确定输出”吗？

内部状态需要纳入完整条件。相同输入、当前状态及声明的环境条件应产生一致的语义结果；比较行为过程时，还要考虑操作顺序、时间推进和环境事件。只比较 props 不足以判断确定性。

详见[组件设计基础](./component-design-foundations.md)第 3～5 节。

### 组件是否应该完全没有副作用？

渲染和派生计算保持纯净。焦点、滚动、定位、监听和清理等可以属于必要的平台交互；应用数据请求、持久化和应用流程由外部负责。复制、预览和媒体等可选能力是否内置仍需分别确定。

详见[组件设计基础](./component-design-foundations.md)第 7 节。

### 受控和非受控是整个组件的分类吗？

它们描述某个状态的权威来源。一个组件可以同时具有受控值、非受控展开状态和内部高亮状态。默认值变化、控制模式切换、重置和事件规则需要公共规范进一步约定。

概念与职责见[组件设计基础](./component-design-foundations.md)第 6、12、13 节；值、状态和事件的具体场景见[公共组件契约规范](./component-contract-standard.md)。

### 输入形式、属性角色与状态所有权如何区分？

输入形式说明组件通过哪类逻辑契约接收内容，例如属性、内容区域和上下文依赖；属性角色说明普通数据与配置、受控值、初始值的不同用途；状态所有权说明谁决定某个状态的有效值。

例如 Select 的 `value` 是属性，角色是提供受控选中值，选中状态由应用决定；选项内容属于内容区域，即使 React 用 prop 传递也不改变其语义。上下文可以提供主题等配置，组件同时接受主题属性时还需要声明覆盖关系。

这些维度分别描述，互斥规则作用于同一维度中的逻辑声明，不要求各框架的传参语法互斥。具体分类、来源关系与场景见[公共组件契约规范](./component-contract-standard.md)。

### 所有组件都需要公开方法吗？

组件可以完全通过声明式输入和事件协作。聚焦、滚动或选择文本等行为可按需要提供公开方法；内核存在打开、选中等命令，不代表这些命令需要对应用公开。

公开方法是可选接口，其调用属于运行时触发，不能绕过受控状态所有权。适用场景与契约要求见[公共组件契约规范](./component-contract-standard.md)。

### 规范、描述文件与开发能力如何协作？

公共规范约束组件契约，描述文件表达结构化契约及能力引用。工程工具和 AI 基于这些契约复用或补建所需能力，形成组件实现，再通过验收条件检查结果。

描述文件需要与工程能力基础共同发挥作用。工程能力基础包括共享内核、平台模块、框架适配、设计资源及开发验证工具等；共享内核是其中负责框架无关组件行为的部分，包含公共状态机制及各组件共享行为，供各框架复用同一份行为实现。

详见[总览](./cross-framework-component-architecture.md)第 1.1、6 节。

### 组件设计基础是否覆盖全部规范与能力设计？

组件设计基础是总览的一份补充，集中定义组件语义与职责。公共契约、描述格式、内核协议、平台交互、框架适配、设计样式、无障碍、兼容、能力目录、验证及生成维护等主题需要各自的详细规范或设计。

[公共组件契约规范](./component-contract-standard.md)已有输入形式、属性角色、状态所有权、事件与可选方法的草案及场景验收；其他主题的内容与状态见总览目录。

详见[总览](./cross-framework-component-architecture.md)第 2 节。
