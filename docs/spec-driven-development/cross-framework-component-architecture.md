# 跨框架组件库架构与规范驱动开发

日期：2026-11-13

状态：设计草案。核心接口、生成策略与实施顺序尚未定稿。

## 1. 目标与范围

以公共规范、组件契约和可复用实现为基础，通过结构化描述、工程工具和 AI 辅助生成、维护及验证组件实现。目标是构建不绑定特定前端框架的组件体系，通过统一契约与适配机制接入不同框架，并支持原生 JavaScript 使用。

组件的框架无关行为由共享内核实现，通过统一的状态读取和订阅协议驱动各框架 UI。框架适配器接入各自的响应式机制与生命周期。统一组件语义和行为，同时允许各框架采用符合其生态习惯的 API。

当前架构设计与验证面向浏览器中的 Web 组件及其交互实现。首批选用 Vue、React、Angular 和浏览器中的原生 JavaScript 验证架构与契约，这一组合不限定架构可接入的框架。其他框架可按相同契约补充面向浏览器的适配与 UI 实现；具体可用性及兼容范围通过实现和验证确认。Web 组件的 SSR 与水合要求仍需单独确定。

开发能力由规范、共享内核、平台模块、框架适配、设计资源及验证工具链共同提供。组件描述文件表达具体组件的契约和所需能力，AI 在这些约束与实现基础上工作；描述文件本身不提供完整开发能力。

当前关注独立于具体产品的通用组件架构，不受某个项目现有模块和目录结构约束。本文不评估或制定具体项目的改造与迁移方案。

当前不覆盖：

- 数据层的描述文件驱动开发、架构设计或重构。
- 特定产品或专业领域的流程、协议和运行时；后续需要时另建领域文档。
- 具体 Schema、完整 UI 描述语言、代码生成器或包发布方案的实现。
- React Native 等非 DOM 平台的具体适配与实现设计；非浏览器平台仅保留扩展边界，不承诺支持。

组件可以管理契约范围内的交互状态，但应用数据获取、持久化和应用流程仍由外部负责。必要的焦点、滚动和定位等平台行为属于组件职责，不能将这一边界简化为“组件整体没有副作用”。

### 1.1 关键概念与关系

| 概念 | 含义 |
| --- | --- |
| 公共规范 | 各组件共同遵守的设计、行为、兼容与验收规则 |
| 组件契约 | 某个组件的输入输出、状态、交互规则、内容区域、平台行为和验收条件 |
| 组件描述文件 | 组件契约的结构化载体，可表达能力引用并连接代码与解释文档；具体格式与字段待定 |
| 共享内核 | 实现框架无关的组件行为，包括公共状态机制及各组件的共享行为 |
| 工程能力基础 | 支撑组件开发与验证的能力集合，包括共享内核、平台模块、框架适配、设计资源及开发验证工具等 |
| AI 辅助开发 | 在规范和能力接口约束下，结合现有实现与验证反馈完成开发任务 |
| 规范驱动开发 | 以公共规范和组件契约为依据，组织实现、生成、维护及验证的开发方式 |

公共规范约束组件契约，组件契约通过描述文件、接口定义与解释文档表达。工程工具和 AI 基于这些契约复用或补建所需能力，形成组件实现；验收条件用于验证实现是否符合契约。

描述文件提供结构化信息，工程能力基础提供实现与工具支持，二者共同支撑开发。共享内核是工程能力基础的一部分，负责复用框架无关的组件行为。框架适配与 UI 连接共享行为和框架机制，使同一组件在不同实现中保持一致语义。

## 4. 各部分职责与边界

### 4.1 组件描述与规范

公共规范定义命名、事件约定、受控模式、无障碍基线和兼容性规则；组件规范定义具体组件的属性、事件、内容区域、状态、命令、行为及验收条件。

描述文件同时供 AI、校验程序、文档工具和开发者使用。建议用 YAML / JSON 表达可校验契约，Markdown 解释设计意图及复杂行为，JSON Schema 校验结构。具体格式、最小字段及扩展机制仍待评审。

初期避免设计过度复杂的通用 UI 描述语言。默认 UI 结构约束到什么程度、复杂算法和渲染扩展如何与描述文件连接，尚未确定。

描述文件用于驱动开发阶段的生成、维护和验证。发布组件独立运行，不依赖 AI 服务；是否还提供运行时描述解释能力并非当前已确定的方案。

### 4.2 共享内核

建议使用纯 TypeScript，负责组件框架无关的行为。例如 Select 的有效选中值、搜索条件、候选项派生、高亮状态，以及 select、open、close 等命令。外部提供候选数据，内核不承担远程查询。

内核不依赖具体前端框架，不直接访问 DOM，也不接管应用请求、持久化及应用流程。

推荐接口方向为“状态快照 + 变更订阅 + 命令”：

- 快照读取当前有效状态。
- 订阅通知状态发生变化，适配器据此读取快照。
- 命令执行声明的交互规则，按契约转换状态或提出修改请求。

内核命令属于共享行为接口，不必公开为组件方法。是否提供供应用调用的命令式接口，由具体组件契约决定。

避免让各框架从零散事件拼装各自的权威状态。语义事件与状态订阅需要区分，具体发布接口及先后关系待定。

需要进一步明确：

- 快照引用稳定性、不可变性及嵌套对象规则。
- 更新是否原子完成，批量通知的边界与时机。
- 订阅初始行为、释放规则、重复订阅及错误处理。
- 命令与外部输入同步的接口及生命周期。
- 受控有效值、候选值和内部状态之间的关系。
- SSR 的初始快照与水合一致性。

受控与非受控模式遵循组件设计基础文档中的状态所有权原则。外部同步不能被误当作新的用户修改请求，造成循环更新。

共享内核是行为复用边界，不要求每个组件都创建 Store，也不要求所有内部状态进入公共快照。纯展示组件可以直接消费属性；编辑器和平台模块可以拥有各自职责范围内的状态。

### 4.3 平台交互层

负责运行环境相关行为，当前设计 Web / DOM 实现，包括焦点管理、键盘事件、外部点击、滚动定位、DOM 测量和弹层定位。同一浏览器能力需要供多个框架复用，因此保留平台交互层；这些模块可以依赖浏览器能力，尽量不依赖具体框架。

平台层将原始操作和观察结果转成组件所需的输入，并执行契约范围内的平台动作。具体键盘含义等行为规则应与共享内核划清责任，避免在不同框架实现中重复定义。

通过 DOM 元素引用及按具体能力定义的接口连接 UI；接口围绕焦点、测量、定位等实际需求确定，不提前设计覆盖所有平台的统一抽象，也不要求独立拆包。等待渲染后才能执行的操作，由框架适配器协调时机。平台资源的创建、订阅、失效和释放需遵循组件设计基础文档。

复制、文件预览、媒体等可选能力是否内置，需要分别评审，不能因使用浏览器 API 就自动认定属于默认组件能力。

非浏览器平台仅保留扩展边界。框架接入与平台适配是不同问题；React Native 等非 DOM 平台的元素、事件和渲染机制不纳入当前设计或验证，不据此承诺其可用性。未来若扩大平台范围，需要重新评审契约适用性与能力边界。

### 4.4 框架适配层

将内核状态接入框架原生响应式机制，同步输入属性，映射对外事件，管理订阅与生命周期，协调渲染后的平台操作。

框架接入遵循通用适配契约，不采用封闭的框架清单。以下以浏览器中的首批验证对象说明接入方向：

| 运行方式 | 接入方向 |
| --- | --- |
| React | 用 useSyncExternalStore 接入外部状态，并满足快照稳定性及 SSR 要求 |
| Vue | 用 shallowRef 等机制承接快照并同步更新 |
| Angular | 将快照更新桥接到 Signal，接入输入、输出与销毁机制 |
| 原生 JavaScript | 直接订阅并驱动渲染；不需要模拟某个框架的响应式系统 |

这些是适配方向，不是已验证的版本兼容承诺；具体实现需按支持的框架版本验证。其他框架可以补充面向浏览器的适配和 UI，继续复用共享内核与适用的平台能力，无需按框架复制共享行为。

适配层保持轻量，组件行为规则集中在共享实现中。控制器销毁权归创建者；共享实例不能因某个使用方卸载就直接销毁。原生 JavaScript 入口也需要清楚的创建、更新和销毁契约。

### 4.5 UI 结构层

负责实际元素结构、插槽或内容投影、ARIA 属性、事件绑定和元素引用，连接框架适配、共享行为及平台交互。

可提供默认 UI，并允许开发者在声明的范围内自定义结构，从而支持无样式组件与完整样式组件。自定义后哪些语义关系、事件和焦点责任必须保留，遵循组件设计基础文档及具体组件契约。

各框架采用自身习惯，不要求组件语法完全相同。跨框架公共语义相同，不意味着 DOM、插槽语法或渲染函数签名必须一致。

默认 UI 和自定义 UI 都不能将原本属于外部的数据请求或应用流程重新隐藏到渲染实现中。

### 4.6 设计与样式层

负责颜色、尺寸、间距、排版、主题、视觉变体和动画，并定义组件部位及状态对应的稳定样式接口。例如 Select 的触发器、面板、选项、高亮项和禁用项。

结构、状态与样式之间需要有明确接口，方便主题替换和自定义。公开部位、状态标识与 Token 应区分于内部 DOM 和实现选择器。

样式复用不要求共享全部结构。框架特有的样式作用域、浮层渲染位置和动画时机，需要在具体方案中验证。主题选择控件不因此获得应用偏好的持久化职责。

### 4.7 验证与交付体系

共享内核验证状态规则；平台交互在浏览器中验证键盘、焦点和环境行为；框架实现验证绑定、输入同步与生命周期；视觉测试验证样式。共同规范用于检查跨框架语义一致性。

验收应覆盖用户和开发者可观察的契约，例如受控更新、事件载荷、键盘导航、资源释放与自定义内容的行为。避免把某种内部实现顺序当成跨框架统一目标。

AI 可以生成测试，但关键验收条件应来自规范并经独立审查，不能仅凭生成实现与生成测试相互吻合认定正确。

交付还包括示例、文档、构建、打包、版本管理及发布。正式产品文档需要描述目标版本实际公开的能力，不能提前把架构目标写成已实现事实。

## 5. 协作与依赖方向

以下是职责约束方向，详细接口仍待评审：

| 部分 | 协作关系与边界 |
| --- | --- |
| 描述与规范 | 在开发、验证和交付中约束各实现，不被等同于运行时 UI 解释器 |
| 共享内核 | 提供框架无关行为；不反向依赖框架组件、DOM 实现或应用数据层 |
| 平台交互 | 当前连接浏览器环境与行为接口；不绑定某一框架 UI 或应用流程 |
| 框架适配 | 桥接共享状态、框架生命周期和平台执行时机 |
| UI 结构 | 按框架方式组合适配与平台连接，提供内容区域和元素引用 |
| 设计与样式 | 通过组件部位、状态及 Token 契约作用于 UI |
| 验证与交付 | 检查各部分及组合结果，贯穿开发流程 |

以 Select 为例：应用传入选项和受控值；用户在 UI 中操作；平台模块识别操作，组件行为产生候选选择；适配器按框架约定输出请求；应用传回新有效值；共享状态更新并通知 UI。打开面板后的测量、定位与焦点操作由适配器协调渲染时机。

这只是协作示例，不确定每个命令、通知或事件的具体 API，也不要求所有交互经过完全相同的调用路径。

## 6. AI 生成与编排系统

AI 系统属于横向开发工具链，不进入组件运行时。发布产物应独立运行。

### 6.1 支撑开发的能力基础

描述文件表达具体组件需要满足的契约，开发体系还需要提供可复用的代码、规则及执行工具。建议逐步建立下列能力：

| 能力基础 | 提供的内容 | AI 开发时的作用 |
| --- | --- | --- |
| 公共规范与组件设计基础 | 状态所有权、事件语义、副作用边界、无障碍及兼容要求 | 约束设计与实现的语义，减少每次重新解释基础概念 |
| 共享内核基础设施 | 快照、订阅、输入同步、命令和生命周期协议及公共实现 | 复用状态机制，在统一协议下实现各组件行为 |
| 组件共享行为 | 各组件的状态规则、派生数据和交互命令 | 同一组件的各框架 UI 调用同一份行为实现 |
| 平台能力模块 | 当前 Web / DOM 的焦点、键盘事件接入、定位、滚动、测量及清理 | 复用环境行为，避免按框架重复实现 |
| 框架适配基础 | 状态桥接、输入输出映射、生命周期和渲染时机连接 | 在统一契约下处理框架差异 |
| 设计资源与结构约定 | Token、主题、组件部位、状态样式及可用基础组件 | 为 UI 和样式提供可复用资源与连接约束 |
| 开发与生成工具 | 描述校验、依赖解析、模板、类型及文档生成、任务执行 | 执行能够确定性完成的工作，组织 AI 需要处理的部分 |
| 验证与交付工具 | 契约验收场景、框架验证入口、构建和发布检查 | 用可执行反馈检查产物，支撑修复与审查 |

这些是需要建设的能力类别，具体实现的可用状态需另行确认，也不要求在第一个组件开始前一次性完成。可先建立最小协议与验证链路，再随组件需求逐步补足。

共享内核包括公共状态机制和各组件的共享行为；统一协议不要求所有组件采用同一套状态字段或一个万能 Controller。共享机制按需要复用，具体行为仍需按组件契约实现和验证。

一轮开发应明确哪些能力已经存在、可以直接复用，哪些需要新增或调整。描述文件中出现某个能力引用，不代表该能力已经实现；缺失能力需要作为显式开发任务处理。

### 6.2 复用、生成与 AI 任务的分工

- 已有共享内核、平台模块和适配基础作为代码依赖复用，并保持明确的版本与接口。
- 可以确定性生成的类型、映射或文档内容，由相应工具处理；具体可生成范围仍待设计。
- 新增行为、框架 UI 及扩展实现可以由 AI 辅助开发，但须遵守现有契约、能力接口和验收条件。
- 公共能力的新增或修改需要单独验证其影响范围，再检查使用它的组件；不能只验证当前生成的界面。

例如开发 Select 时，可以复用已有状态订阅、焦点、定位、框架桥接和 Token，在这些基础上实现并验证 Select 的选中、高亮和展开规则，再连接各框架 UI。若选中规则已经实现，则优先复用并验证差异；若尚未实现，则显式补建这一份共享行为。

这使组件描述能够指导增量开发、维护及验证，而非要求每次重新生成整套基础设施。人工修改与重新生成的所有权规则仍需进一步评审。

### 6.3 建议开发流程

建议流程：

1. 校验组件描述与公共规范。
2. 解析共享行为、平台能力、框架适配、Token、基础组件及其他依赖，识别可复用能力与缺口。
3. 基于现有实现、框架规则和模板，补建缺失能力，生成或更新组件行为、适配、UI、样式、文档及测试。
4. 执行类型检查、构建和必要验证。
5. 根据错误进行有限次数修复；次数、停止条件和失败处理另行确定。
6. 审查代码、行为与视觉差异后，按发布流程交付。

共享内核维护一份，由各框架共同调用。生成过程不应为每个框架复制一份本应共享的行为实现。

记录规范、模板、适配器、提示词及模型版本，以便追踪生成结果和回归问题。版本记录帮助追溯，不等于保证模型重新生成完全相同的代码。

人工修改、扩展入口、生成内容所有权和重新生成策略尚未定稿。需要避免同一段代码既被视为可以覆盖的生成物，又允许无法追踪的人工修改。

## 7. 验证组件与演进范围

首批在浏览器中选用 Vue、React、Angular 和原生 JavaScript，检查共享行为、适配契约、Web / DOM 平台交互、UI 接入及跨实现语义一致性。这一验证选择不限制其他框架后续接入，不包含非 DOM 平台验证。

建议使用 Select 验证共享内核与多框架接入，结合 Button、Input、Dialog 覆盖不同复杂度：

| 组件 | 可验证的主要问题 |
| --- | --- |
| Button | 输入输出、原生语义、禁用、基础样式及简单框架映射 |
| Input | 值与默认值、受控同步、输入法、校验及表单关联 |
| Select | 状态组合、派生选项、候选值、键盘、焦点及弹层定位 |
| Dialog | 打开状态、内容定制、焦点、模态行为、挂载与清理 |

具体验证组件、功能子集、框架版本和执行顺序仍待确定。本表不构成实施计划，也不承诺一次实现全部组件能力；非浏览器平台不在当前范围内。

先用通用组件验证架构，再按需要补充专业领域组件契约。专业领域文档应补充领域语义，而不重复维护一套通用状态和副作用规则。

## 8. 待定设计问题

1. 描述文件的最小字段、格式、扩展机制及与代码引用的关系。
2. 七个部分是否需要合并或拆分，以及可检查的依赖约束。
3. 内核的快照、订阅、批量更新、命令及销毁接口。
4. 受控与非受控的统一协议，以及状态通知、修改请求和对外语义事件的区别。
5. 平台交互与框架适配如何衔接 DOM 引用及渲染时机。
6. 默认 UI 是否由描述文件表达、可定制范围、组件部位及样式接口。
7. SSR、水合、稳定 ID 及平台能力缺失时的规则。
8. 人工修改、扩展、重新生成策略及生成内容所有权。
9. 各部分验收标准、首批验证组件、框架版本及具体验证覆盖范围。
10. 哪些内容确定性生成，哪些由 AI 辅助维护，哪些由人工维护。
11. 最小能力基础如何建立，各组件如何声明能力依赖、检查可用性与版本，并处理公共能力变更的影响。

其中组件职责、状态与平台能力相关的细项继续在[组件设计基础](./component-design-foundations.md)中评审，本文不将其提前定稿。
