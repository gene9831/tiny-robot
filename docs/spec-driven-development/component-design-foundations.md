## 1. 目的与适用范围

本文是[跨框架组件库架构与规范驱动开发](./cross-framework-component-architecture.md)的一份详细补充，回答“组件是什么、拥有什么、负责什么、如何与外部协作”，作为后续组件规范、描述文件和跨框架实现的基础。

组件模型由输入、状态、操作与输出构成；行为契约规定可观察结果；职责边界明确组件与应用如何协作。状态所有权、平台行为、生命周期、无障碍和可定制范围共同构成组件设计基础。

架构总览负责七个职责部分、协作关系、可复用能力基础及 AI 工具链定位；本文展开其中各实现共同遵守的组件语义、行为契约与职责边界。公共契约的具体约定、内核协议、平台能力、框架适配、描述格式、设计样式、验证和开发工具等仍需其他补充文档，主题与位置预留在总览第 2 节。

本文定义公共组件语义，不替代具体协议或能力实现。

适用于展示、输入、选择、浮层、列表、布局等通用 UI 组件，包括有样式组件、无样式组件和复合组件。原则不绑定特定前端框架，当前设计与验证面向浏览器中的 Web 组件及其交互实现，首批采用 Vue、React、Angular 和原生 JavaScript。非浏览器平台仅保留扩展边界，不展开 React Native 等非 DOM 平台的具体设计；Web 组件的 SSR 与水合要求仍保留为待决项。

本文不定义：

- 特定产品或专业领域的状态、协议和流程；领域规则后续另文记录。
- 数据层的内部架构、接口或实现。
- 组件描述文件的格式、Schema、代码生成和重新生成机制。
- npm 拆包、框架版本和具体响应式接入方案。
- 既有组件的迁移计划或行为变更。

## 2. 组件的定义

> UI 组件是具有明确输入、状态、交互规则和输出的可组合界面单元，负责内容呈现、用户交互、无障碍语义及必要的平台行为。组件通过公开契约与外部协作，应用数据的获取、持久化及应用流程由外部负责。

组件职责不以代码量、是否异步、是否含有内部状态判断。复杂的键盘导航可以属于组件，简单的一次接口查询也可能属于外部数据层。

组件可以由多个子组件组成，也可以提供供高级定制使用的行为实现。内部拆分方式不改变整体公开契约。

### 2.1 术语

| 术语 | 本文含义 |
| --- | --- |
| 用户 | 实际操作界面的最终用户 |
| 应用 | 向组件提供输入、处理事件并决定应用后续行为的外部代码 |
| 调用方 | 调用组件方法或命令式 API 的代码 |
| 公共契约 | 明确承诺的输入、状态语义、输出、交互规则、平台行为及兼容性要求 |
| 有效值 | 当前用于组件语义与呈现的值，按受控或非受控规则确定 |
| 候选值 | 一次交互希望产生的新值；不一定已被应用接受 |
| 内部状态 | 组件拥有并管理的状态，不表示所有此类状态都属于公共 API |
| 平台行为 | 为实现组件交互而使用运行环境能力的行为；当前指 Web / DOM 环境中的焦点、测量和滚动等行为 |
| 副作用 | 计算结果之外对状态、资源或外部系统产生的影响；不等同于框架中特定名称的 Effect |

## 3. 确定性与渲染纯度

### 3.1 完整条件相同时，语义结果一致

“确定输入带来确定输出”不能简化为“相同 props 永远显示相同界面”。当前状态、上下文及环境条件都可能影响结果。

```text
界面结果 = render（外部输入，当前状态，声明的环境条件）
下一状态与交互结果 = transition（当前状态，输入，操作或环境事件）
```

这是职责模型，不要求实现必须采用特定函数或状态机库。环境观察结果可以先进入状态，再参与渲染；不要求渲染时直接读取浏览器。

在相同初始条件、相同输入变化、相同操作顺序和相同环境事件下，组件应产生一致的可观察行为。时间推进、异步完成和尺寸变化也属于需要考虑的条件。

| 场景 | 解释 |
| --- | --- |
| Accordion 点击后展开，props 未变化 | 内部展开状态变化，符合确定性 |
| Select 连续两次按方向键得到不同高亮项 | 每次操作前的状态不同，符合确定性 |
| Popover 在窗口边缘改变方向 | 位置依赖元素尺寸与可视区域，应声明定位规则 |
| Tooltip 延时显示 | 延时配置和计时器到期事件参与行为 |
| 日期在不同语言或时区下显示不同 | 语言、时区和格式化策略需要有明确来源 |
| 渲染时随机决定选中项 | 引入未声明的隐藏条件，不符合可预测性要求 |

跨框架一致性主要比较值、交互、事件和无障碍语义。允许符合框架习惯的接口及内部结构差异；不要求生成完全相同的 DOM 或像素结果。

### 3.2 渲染与派生计算保持纯净

渲染、筛选、格式化及派生值计算不执行请求、持久化、对外事件发送、焦点移动等动作，也不修改输入对象或其他实例状态。重复计算不应造成这些动作重复发生。

渲染纯净不禁止通过声明式结果更新界面，也不禁止交互过程中更新组件拥有的状态。它约束的是计算阶段与外部可观察动作的分离。

当前时间、随机性、默认语言及用户偏好等依赖需要有明确来源。稳定标识的创建应具备实例与 SSR 语义，不能依赖渲染次数随意变化。

## 4. 输入与输出

### 4.1 输入的范围

公共输入声明按逻辑用途区分形式，属性再说明其使用角色，状态另行确定所有权。三个维度分别回答“以什么契约提供”“如何使用”和“谁决定当前有效值”，不能混成一个互斥分类。

本架构采用以下声明形式；具体契约见[公共组件契约规范](./component-contract-standard.md)。

| 声明形式 | 示例 | 要求 |
| --- | --- | --- |
| 属性 | 选项、禁用状态、当前值、初始值、格式化函数 | 分别声明类型、使用角色、缺省和空值、更新语义及关联状态 |
| 内容区域 | 标题、默认内容、选项内容及其渲染函数 | 明确可替换范围、可读取数据及保留的行为责任 |
| 上下文依赖 | 主题、语言、方向、容器 | 明确提供范围、缺失行为与同名属性的优先级 |

这是一种跨框架的逻辑声明划分，不要求框架语法互斥。React 的 `children` 或内容渲染函数可以通过 prop 传递，Vue 使用插槽，Angular 使用内容投影；它们都可对应同一个内容区域契约。同一设置若支持属性和上下文两个入口，需要分别声明入口及覆盖规则。

属性的普通数据与配置、受控值、非受控初始化值属于使用角色。例如 `options` 提供选项，`value` 绑定选中状态的外部权威值，`defaultValue` 提供非受控初始化值。一个属性的角色不能推导整个组件的所有权。

组件运行时还接收输入变化与触发事件：用户操作、属性或上下文更新、生命周期事件、平台观察及异步动作结果。它们描述行为何时发生，不与上述公共声明形式放在同一分类中。公开方法的调用仅在组件提供相应接口时成为运行时触发，见第 4.3 节。

输入对象及其嵌套内容按只读契约使用。组件需要排序或筛选时产生派生结果；需要修改外部记录时，通过事件或明确接口请求应用执行。

传入的渲染或格式化函数如果参与纯计算，也需要遵守纯计算约束。通过回调隐藏副作用不会改变职责边界。

### 4.2 输出的范围

输出包括界面、无障碍语义、公开状态、语义事件、方法结果及声明的平台行为。内部 DOM、辅助状态或第三方实例不因“能够观察到”而自动成为公共 API。

例如，按钮的输出既包括文本与禁用样式，也包括可访问名称和激活语义；Dialog 的契约还包括键盘和焦点行为。

### 4.3 可选的公开方法与命令

组件可以不提供公开方法。能由属性、内容、上下文和事件表达的协作，优先使用声明式接口；聚焦、滚动到指定项、选择文本等行为，可以按需要提供命令式接口。React 和 Vue 的官方文档均建议限制组件引用及命令式接口的使用范围。[React 指南](https://react.dev/reference/react/useImperativeHandle)、[Vue 指南](https://vuejs.org/guide/essentials/template-refs.html#ref-on-component)

共享内核的命令供 UI 和适配器组织交互，不自动成为公开组件方法。Select 内部可以执行打开或选中命令，而公共接口只通过属性与事件协作。

如果选择公开方法，需要声明参数、返回值、执行条件、失败及取消、平台动作结果和状态所有权。Input 的 `focus()` 不能被理解为改变文本值；Dialog 的打开状态宜由属性表达，若另行提供 `close()`，也不能绕过受控打开状态的权威来源。

## 5. 状态的分类与所有权

每一项状态应有明确的权威来源。同一值不能同时由应用与组件独立决定，再通过偶然的同步顺序竞争最终结果。

下表概览常见状态与相关数据的用途，不是互斥的所有权分类。内部、派生、可交互等描述不同方面，具体权威来源仍需逐项确定。

| 状态类别 | 示例 | 责任 |
| --- | --- | --- |
| 可交互值 | 文本、选中项、展开状态、当前页码 | 按公开契约由应用或组件拥有 |
| 临时交互状态 | hover、高亮项、拖拽过程、输入法组合状态 | 通常由组件内部拥有 |
| 派生状态 | 过滤结果、字符数、是否允许提交 | 根据权威输入和状态计算，不作为另一份独立事实 |
| 平台观察状态 | 尺寸、实际焦点、滚动位置 | 由平台模块观察，与组件交互同步 |
| 外部应用数据与运行状态 | 服务端记录、上传进度、权限、请求错误 | 应用提供；组件负责消费与展示 |

组件可以管理非受控选中值等有语义的状态，不局限于 hover 等临时状态。拥有状态也不意味着拥有其持久化职责。

不必公开全部内部状态，也不必让全部状态可受控。纯展示组件不需要为了架构形式创建状态容器。

对复杂编辑控件，可以让编辑器拥有文档、选区和撤销历史，再通过明确接口连接组件。避免维护两份含义相同、更新权限不清的完整状态。

## 6. 受控与非受控

### 6.1 按状态维度定义

受控与非受控描述某个状态的所有权，不是整个组件的固定类别。Select 可以同时具有受控选中值、非受控展开状态及内部高亮状态。尺寸、颜色等配置属性不需要机械地提供非受控版本。

| 项目 | 受控模式 | 非受控模式 |
| --- | --- | --- |
| 有效值来源 | 应用传入的值 | 组件拥有的内部状态 |
| 初始化 | 使用外部值 | 根据默认值或声明规则初始化 |
| 用户操作 | 产生候选值，提出修改请求 | 更新内部有效值并按契约通知 |
| 应用未接受候选值 | 有效值继续服从外部输入 | 应用未处理通知不影响已完成的内部更新 |
| 外部更新 | 应用传入新值 | 通过已声明的重置或命令契约处理 |

受控 Select 当前值为 A，用户点击 B，组件提出选择 B 的请求；应用传入 B 后，B 才成为有效值。焦点、按压反馈等临时状态仍可内部管理。

复杂输入可以具有尚未提交的编辑草稿，但必须区分草稿与受控有效值，并定义输入法组合输入、提交、取消及外部更新的协调规则。

### 6.2 每个可受控状态需要说明的内容

- 受控模式的识别条件，及 `undefined`、`null`、空字符串、空数组的含义。
- 值、默认值、更新请求之间的关系，以及同时传入时的处理。
- 初始化、用户操作、外部同步和显式命令的行为。
- 应用拒绝或转换候选值时的呈现与事件规则。
- 控制模式是否允许切换；允许时状态如何交接。
- 默认值后续变化、重置及重新创建实例时的行为。
- 输入失效时的策略，例如选中项被移除、页码超过范围。

“受控”不表示“不可编辑”。用户可以提出修改，只是有效值由应用决定。只读、禁用与受控是不同维度，应分别定义。

如果组件提供公开方法，方法也不能绕过状态所有权。例如受控 Dialog 选择公开 `close()` 时，应说明它是否提出关闭请求或具有其他明确语义，不能暗中覆盖受控值；该例不要求 Dialog 必须提供此方法。

## 7. 副作用与外部责任

### 7.1 职责基线

> 渲染与派生计算保持纯净；组件只执行契约范围内、为呈现和交互所需的平台行为。应用数据获取、持久化及应用流程由外部负责。

不能用“是否异步”区分职责。等待渲染、动画结束或复制完成可以属于组件；一次同步 storage 写入仍可能越过组件边界。

### 7.2 行为分类

| 行为 | 归属 | 要求 |
| --- | --- | --- |
| 本地筛选、排序、字符计算和同步规则校验 | 组件计算 | 输入明确，不修改原始数据 |
| 焦点、滚动、尺寸测量、定位 | 组件平台交互 | 触发条件与影响范围明确 |
| 监听器、Observer、动画、交互计时器 | 组件平台交互 | 生命周期内安装，失效时停止并释放 |
| 编辑器等界面实例的创建与同步 | 组件集成 | 明确实例和订阅的所有权 |
| 剪贴板、本地文件预览、媒体设备 | 可选平台能力 | 是否内置须按能力确认，见第 13 节；不能仅因是平台 API 就默认允许 |
| 查询接口、文件上传、应用 WebSocket | 外部数据层 | 组件提出意图，应用回传数据与运行状态 |
| 读取或写入应用 storage、缓存及数据库 | 外部数据层 | 避免隐藏输入与持久化耦合 |
| 路由、埋点、权限和跨页面流程 | 外部应用层或集成层 | 通过明确输出与应用协作 |

数据层与应用层均在组件边界之外，但不要求它们合并为同一个模块。

### 7.3 容易误判的情况

**读取也可能引入耦合。** 主题控件自行读取 localStorage 的历史值，会让初始化依赖隐藏输入。应用应先读取偏好，再向组件提供主题值。

**回调不会自动改变职责。** Select 接收 `loadOptions()`，再负责请求时机、缓存、重试和竞态，仍属于数据编排。符合本文边界的默认接入方式是输出搜索意图，由应用回传选项、加载状态及错误。

**声明式资源加载需要单独判断。** Image 根据传入 URL 让浏览器加载资源，可以属于公开呈现能力；不能仅凭出现网络流量认定越界。组件不应借此附加未声明的数据查询、鉴权或应用缓存策略。

**用户操作不自动授权应用流程。** 点击确认可以触发确认事件，但不能仅凭这一操作就让通用 Dialog 知道应删除哪个服务端实体。

## 8. 事件与方法的语义

### 8.1 区分意图、值与结果

| 类别 | 含义 | 示例 |
| --- | --- | --- |
| 操作意图 | 用户希望执行某项动作 | 提交、取消、删除、重试 |
| 状态修改请求 | 希望某项状态采用候选值 | 请求选择 B、请求关闭 |
| 有效状态变化通知 | 状态已按所有权规则发生变化 | 非受控选中值从 A 变为 B |
| 平台动作结果 | 某项平台操作完成或失败 | 复制成功、播放失败 |

这是一种语义分类，不要求每个组件都提供四套事件，也不预先决定事件名称。

确认事件不表示删除成功，提交事件不表示服务端已收到数据。若组件报告平台动作结果，需要以动作的实际结果为依据。

外部值同步不能再次被当作用户输入，形成更新请求循环。若需要报告有效值变化，应明确事件来源及其与用户操作事件的区别。

### 8.2 每项事件或方法应说明

- 触发条件、载荷或参数、结果以及失败方式。
- 是操作意图、修改请求还是已发生结果。
- 受控与非受控模式是否不同。
- 用户操作、外部同步和方法调用是否会触发它。
- 是否可取消，取消影响什么，以及与其他事件的先后关系。
- 异步行为的重复调用、失效和组件销毁规则。

不能直接依据框架中的 `change`、`update` 或 `emit` 等名称推断语义；各框架接口应映射到同一公共契约。

## 9. 生命周期、平台资源与实例隔离

- 创建资源的主体负责释放；订阅方负责释放自己的订阅。
- 使用外部共享实例的组件卸载时，不能擅自销毁该实例。
- DOM 操作需要协调渲染完成时机，不在纯计算阶段执行。
- 计时器、监听器、Observer、临时对象 URL 等资源需要有清理路径。
- 旧异步结果不能在操作失效、对象切换或组件销毁后覆盖新的有效状态。
- 多实例不能意外共享可变状态；浮层栈、焦点协调等有意共享机制需要明确作用域。
- SSR、水合与平台能力缺失时的支持范围、初始化和降级策略需要明确。

例如，Tooltip 关闭后尚未结束的显示计时器应失效；卸载一个订阅共享控制器的组件，只解除该组件的订阅。

## 10. 无障碍、原生语义与可定制范围

组件职责包括可访问名称、语义关系、键盘导航和焦点行为。无障碍不能仅理解为补充 ARIA 属性。

优先保留适用的原生元素行为。自定义结构替代原生元素时，需要继续满足对应交互契约。模态 Dialog 的焦点进入、Tab 导航和关闭后的焦点恢复属于组件责任。

禁用、只读、加载和错误状态需要分别定义其值变化、激活、焦点和呈现语义，不能简单共用一条“阻止操作”规则。

插槽、渲染函数、内容投影和无样式接口应说明：

- 哪些结构与样式可以替换。
- 哪些事件、元素引用和语义关系必须保留。
- 替换后由组件还是应用承担相应的无障碍责任。
- 扩展内容可以读取哪些状态、提出哪些动作。

自定义选项内容不应无意破坏 Select 的选择与键盘行为；完全替换触发器时，需要明确焦点和事件连接方式。

## 11. 通用场景的职责示例

以下是边界示例，不承诺任何项目已实现对应组件或接口。

| 场景 | 组件负责 | 应用负责 |
| --- | --- | --- |
| Button 执行保存 | 激活、禁用、显示传入的处理中状态 | 保存请求、错误处理、回传状态 |
| Input 编辑文本 | 编辑交互、输入规则、值修改请求或内部更新 | 受控值接受策略、草稿持久化 |
| Select 本地筛选 | 根据输入选项筛选、高亮、选择与定位 | 提供选项及受控有效值 |
| Select 远程搜索 | 搜索意图、选项呈现、键盘、加载与错误展示 | 查询、缓存、重试、竞态及结果回传 |
| Dialog 确认删除 | 确认与取消、焦点、显示传入的处理中状态 | 删除实体、处理失败、决定何时关闭 |
| Upload / 文件选择控件 | 文件选择、拖放、本地规则校验、移除意图；预览按已确认平台能力执行 | 上传、远程删除、重试和进度回传 |
| Form 校验 | 执行声明的本地规则，展示外部错误 | 远程唯一性校验、最终提交和结果处理 |
| Pagination 切页 | 页码交互、页数计算、切页请求或内部更新 | 获取对应页数据、回传总数 |
| Table 排序与勾选 | 排序交互、选择状态；本地排序按契约执行 | 服务端排序请求、持久化选择、批量操作 |
| Tabs 切换 | 激活、焦点、键盘与面板展示 | 路由同步、内容数据获取、记忆偏好 |
| Tooltip 延时出现 | 触发条件、计时、定位、关闭与清理 | 提供内容与延时配置 |
| 主题切换控件 | 主题选择，按契约在指定范围应用样式 | 偏好加载、持久化及跨设备同步 |
| Image 展示图片 | 按 URL 展示、加载与失败反馈、替代文本 | 提供 URL、访问权限及应用数据 |
| 复制按钮 | 输出复制意图；若确认内置能力，则执行复制并报告结果 | 提供内容、选择平台能力或自定义策略 |

补充约束：

- 远程搜索的防抖需要区分“延迟输出搜索意图”与“延迟执行请求”。前者可属于组件交互配置，后者属于外部请求策略，均需明确。
- 受控 Dialog 请求关闭后，只有有效打开状态改变才执行相应的关闭行为；是否保留退出动画由契约规定。
- 本地文件预览使用的对象 URL 等临时资源由创建者释放；上传地址和上传凭据不属于通用文件选择组件。
- Table 对输入数据执行本地排序时不能原地修改应用传入的数组。
- 加载更多组件可以输出需求与展示进度，但不因此接管远程分页数据管理。

## 12. 建议采用、尚待确认的默认约定

下列策略不是所有框架的统一规则，后续应明确采用或调整：

1. **控制模式保持稳定**：同一状态在实例存续期间默认不切换受控与非受控模式；例外需显式定义。
2. **默认值只初始化**：默认值后续变化不自动覆盖用户操作。重置目标、表单 reset 和重新挂载的关系另行定义。
3. **受控输入优先**：值与默认值同时存在时建议由受控值决定有效值，但需先确定受控识别与诊断规则。
4. **关键语义状态优先支持受控**：如选中值、打开状态；临时状态和测量数据不强制开放。
5. **远程数据通过输入和事件连接**：默认不提供让通用组件接管请求的 loader、缓存或重试接口。
6. **可选平台能力可替换**：若内置复制、预览等能力，应有明确启用方式、失败反馈及替换入口。

## 13. 待决问题

1. 哪些平台能力允许作为组件内置能力：复制、文件读取与预览、下载、音视频播放、麦克风等应分别判断。
2. `undefined`、`null` 与未传属性如何参与受控判断，跨框架适配如何保持语义一致。
3. 更新请求、有效值变化和操作事件的命名、来源标记及顺序是否采用统一规则。
4. 输入失效时采用保留、规范化、回退还是提出修正请求；哪些行为由公共规范规定，哪些交给组件定义。
5. 重置、表单关联、原生提交与浏览器默认行为如何连接，哪些需要明确选择后才启用。
6. 异步扩展回调允许到什么程度；如何避免通用组件通过 Promise 回调重新接管应用流程。
7. SSR、水合、稳定 ID 以及平台能力缺失的最低支持要求。

这些问题不妨碍先确定职责基线，但在形成描述文件契约或实现相关能力前，需要解决对应项。

## 14. 组件职责评审清单

- [ ] 能说明组件解决的界面与交互问题，不含隐式应用流程。
- [ ] 每项输入的来源、只读约束、更新与空值语义明确。
- [ ] 状态分类和权威来源明确，派生状态不成为重复事实。
- [ ] 可受控状态分别说明初始化、更新请求、外部同步、重置及异常输入。
- [ ] 渲染和派生计算可重复执行，不产生额外可观察动作。
- [ ] 事件与方法区分意图、有效状态变化及实际结果。
- [ ] 平台行为声明触发条件、影响范围、失败及清理方式。
- [ ] 请求、持久化和应用流程通过输入与输出连接外部。
- [ ] 键盘、焦点、原生语义和内容定制责任完整。
- [ ] 多实例、共享资源、异步失效和支持环境的边界明确。
- [ ] 未将建议约定、待决项或目标行为当成已确认、已实现的事实。
